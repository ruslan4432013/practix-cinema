# Analytics Collector — сервис сбора пользовательских действий

Аналог Яндекс.Метрики для онлайн-кинотеатра: принимает от браузера клики,
просмотры страниц и кастомные события плеера и поиска, обогащает их серверными
данными и публикует в Kafka.

Главный принцип, которому подчинена вся конструкция: **аналитика не должна
ломать сайт**. Ни падение Kafka, ни падение Redis, ни падение Auth не приводят к
ошибке на клиенте — сервис деградирует, но продолжает принимать события.

## Возможности

* Приём кликов, просмотров страниц (включая время на странице) и трёх кастомных
  событий: смена качества видео, просмотр до конца, использование фильтров поиска.
* Пакетная отправка событий — под сценарий `navigator.sendBeacon`.
* Опциональная аутентификация: анонимы принимаются, при валидном токене событие
  атрибутируется пользователю.
* Публикация в отдельные топики Kafka с партиционированием по пользователю.
* Буфер деградации в Redis с крашоустойчивым фоновым дренажом.
* Дедупликация по `event_id`, ограничение частоты запросов, ограничение размера
  полезной нагрузки.
* Метрики Prometheus, сквозная трассировка в Jaeger, структурированные логи.

зависимостей, что в `rest/db/base.py`. Подробные диаграммы — в
[docs/architecture.md](docs/architecture.md).

## Эндпоинты

| Метод | URL | Описание |
|-------|-----|----------|
| `POST` | `/api/v1/events/click` | Клик по элементу интерфейса |
| `POST` | `/api/v1/events/page-view` | Просмотр страницы и время на ней |
| `POST` | `/api/v1/events/custom` | Кастомное событие (тип в поле `event_type`) |
| `POST` | `/api/v1/events/batch` | Пачка до 50 событий любых типов |
| `GET` | `/health/live` | Проба живости (не зависит от Kafka) |
| `GET` | `/health/ready` | Проба готовности (отражает состояние Kafka) |
| `GET` | `/metrics` | Метрики Prometheus |
| `GET` | `/api/analytics/openapi` | Swagger UI |

Все ручки приёма отвечают `202 Accepted`: событие принято, но подтверждение от
кворума реплик Kafka к этому моменту ещё не получено.

Путь документации отличается от привычного `/api/openapi` — тот за Nginx уже
занят Movies API.

### Пример

```bash
curl -X POST http://localhost/api/v1/events/click \
  -H 'Content-Type: application/json' \
  -d '{
        "session_id": "sess-42",
        "anonymous_id": "anon-77",
        "element_type": "film",
        "target_id": "3d825f60-9fff-4dfe-b294-1a45fa1e115d",
        "page_url": "http://localhost/films/3d825f60-9fff-4dfe-b294-1a45fa1e115d",
        "position": 3,
        "context": {"url": "http://localhost/", "locale": "ru-RU"}
      }'

# {"event_id":"...","status":"accepted"}
```

Поле `status` показывает, что произошло с событием: `accepted` — передано в
Kafka, `buffered` — Kafka недоступна, событие в буфере, `duplicate` — подавлено
дедупликацией, `filtered` — отброшено фильтром до публикации (трафик ботов),
`dropped` — потеряно (недоступны и Kafka, и буфер).

## Безопасность

* **`user_id` берётся только из подписи токена.** Полей `user_id`,
  `is_authenticated` и времени приёма во входных моделях нет вовсе, а
  `extra='forbid'` превращает попытку их передать в 422.
* **Проверка JWT локальная**, общим с Auth секретом — сетевых вызовов на горячем
  пути нет, поэтому недоступность Auth не влияет на приём событий.
* **Сырой IP не покидает процесс**: в Kafka уходит только `blake2b(ip, key=соль)`.
  Соль обязательна при `UGC_ENV=prod` — сервис не стартует со значением по
  умолчанию, а вне продакшена пишет об этом WARNING при старте. Само значение
  `UGC_ENV` проверяется по списку `dev|test|prod`: опечатка вроде `production`
  раньше тихо переводила сервис в мягкий режим.
* **`X-Forwarded-For` принимается только от доверенных сетей**
  (`UGC_TRUSTED_PROXIES`). Иначе при прямом доступе к сервису клиент подделал
  бы заголовок и получал новый счётчик лимита на каждый запрос — то есть лимита
  бы не было.
* **Адрес клиента берётся из `X-Real-IP` или из ПОСЛЕДНЕГО элемента
  `X-Forwarded-For`**, а не из первого. Nginx формирует заголовок как
  `$proxy_add_x_forwarded_for` — присланный клиентом список плюс дописанный
  справа настоящий адрес, — поэтому слева стоит ровно то, что подставил клиент.
  Доверия к левому элементу хватило бы, чтобы менять счётчик лимита на каждый
  запрос и накручивать `ip_hash` в аналитике.
* **Ограничения полезной нагрузки**: размер тела (64 КБ, отсекается до чтения),
  размер пачки (50), длины всех строк, плоский словарь `properties` без
  вложенности.
* **Имя топика недоступно клиенту** — резолвится сервером по типу события.
* **Ограничение частоты** на двух уровнях и по трём ключам: `limit_req` в Nginx
  плюс счётчик в Redis в приложении — по IP, по `anonymous_id` и по
  `session_id`. Одного IP мало с обеих сторон: он бесполезен против ботнета и
  бьёт по легитимным пользователям за общим NAT. Алгоритм — скользящее окно:
  фиксированное позволяло клиенту на стыке окон отправить два лимита подряд.
  Пачка расходует лимит по числу событий в ней. Все ключи одного запроса
  списываются ОДНИМ pipeline (`RateLimiter.consume_many`): на горячем пути
  приёма важна не только стоимость операции, но и число последовательных
  round-trip к Redis.
* **Трафик ботов отсекается до публикации** (`device_type == bot`): краулер,
  обходящий каталог, иначе даёт десятки тысяч «просмотров», за приём, передачу
  и хранение которых надо платить, чтобы потом вычищать их в каждом запросе.
* Контейнер работает без привилегий root.

## Отказоустойчивость

| Что отказало | Поведение |
|--------------|-----------|
| Kafka | Событие уходит в буфер Redis, ответ `202 {"status":"buffered"}`. Фоновый дренаж доставляет накопленное после восстановления. |
| Отдельная «отравленная» запись (слишком большая и т. п.) | Продюсер остаётся здоровым: ошибки уровня записи не переводят брокер в degraded, иначе одно сообщение уводило бы весь поток в Redis. Запись уходит в буфер, а при первом же дренаже — в DLQ (`RecordRejectedError`), не тратя попытки; счётчик — `ugc_records_rejected_total`. |
| Redis | Событие теряется, фиксируется метрикой `ugc_events_dropped_total` и записью ERROR. Rate limit и дедупликация отключаются (fail-open). 5xx не возвращается. |
| Auth | Не влияет: подпись токена проверяется локально. |
| Перезапуск сервиса с непустым буфером | События не теряются: дренаж извлекает записи через `LMOVE` в in-flight-список и удаляет только после подтверждения брокером. |
| Отказ одного брокера Kafka | Запись продолжается: RF=3, `min.insync.replicas=2`. |

## Запуск

Сервис поднимается вместе со всем стеком из корня репозитория:

```bash
docker-compose up -d --build
```

Поднимаются: кластер Kafka из трёх узлов (KRaft), задача создания топиков,
Kafka UI, сам коллектор и демонстрационный консьюмер.

```bash
# Swagger
open http://localhost/api/analytics/openapi

# Kafka UI: топики, партиции, сообщения
open http://localhost:8081

# Поток событий, доехавший до аналитического хранилища
docker compose exec clickhouse-01 clickhouse-client --user etl --password etl \
  -q "SELECT event_type, count() FROM ugc.raw_events GROUP BY event_type"

# Состояние топиков
docker-compose exec kafka-0 /opt/kafka/bin/kafka-topics.sh \
  --bootstrap-server kafka-0:9092 --describe | grep '^Topic: ugc\.'
```

### Локально, без Docker

```bash
cd analytics_collector
pip install -r requirements.txt
cp .env.example .env          # поправьте REDIS_HOST / KAFKA_BOOTSTRAP_SERVERS
uvicorn main:app --app-dir src --reload
```

### Проверка деградации

```bash
docker-compose stop kafka-0 kafka-1 kafka-2
curl -i -X POST http://localhost/api/v1/events/click -H 'Content-Type: application/json' \
     -d '{"session_id":"s","element_type":"film"}'
# 202 Accepted, "status": "buffered"

docker-compose start kafka-0 kafka-1 kafka-2
# через несколько секунд буфер разгружается в Kafka
```

## Дальнейшее развитие

Список того, что осознанно не сделано в объёме спринта, — с причинами, а не
просто перечнем.

### Реестр схем и бинарный формат вместо JSON

Событие сериализуется в JSON, а совместимость держится на договорённости и поле
`schema_version`. Ничто не мешает выкатить продюсера, который начнёт слать новое
поле или изменит тип существующего: консьюмеры сломаются в рантайме, уже после
того как несовместимые данные легли в топик. Kafka сообщения не валидирует — для
неё это байты. Плюс JSON избыточен: имена полей повторяются в каждом сообщении.

Решение — Confluent Schema Registry (или Apicurio) + Avro либо Protobuf. Реестр
отвергает несовместимое изменение схемы **на этапе публикации схемы**, а не на
этапе чтения испорченных данных; Avro на таких сообщениях обычно сокращает объём
в 2–4 раза. Цена — ещё один сервис в стеке и генерация классов из схем в сборке.

### Защита ingest от целенаправленного злоупотребления

Лимиты по IP, `anonymous_id` и `session_id` уже есть, боты отсекаются. Не
сделано:

* **подписанный сервером токен трекера** с коротким TTL, выдаваемый при загрузке
  страницы; событие без него отбрасывается. От целенаправленной атаки не спасает
  (токен виден в браузере), но отсекает примитивные скрипты;
* **квоты продюсера на стороне Kafka** (`client.id`-based quotas) как последний
  рубеж.

### Секреты и ротация соли

Секреты берутся из `.env`, а должны — из Vault / AWS Secrets Manager / Docker
secrets. Отдельно: смена `UGC_IP_HASH_SALT` разрывает связность `ip_hash` с
историческими данными. Правильно хранить версию соли рядом с хешем, но это поле
конверта, а значит колонка в `ugc.raw_events` и изменение `RAW_COLUMNS` в ETL —
изменение схемы, а не локальная правка.

### Сэмплирование и приоритеты потоков

При кратном росте трафика хранить все клики станет дорого. Стоит сэмплировать
массовые и малоценные события (клики по навигации), сохраняя 100 % ценных
(досмотры, покупки). Важно: сэмплировать **детерминированно по `user_id`** (хеш
по модулю), а не случайно, — иначе путь пользователя развалится на несвязанные
фрагменты и станет непригоден для воронок.

### Транзакционный продюсер

`enable_idempotence=True` гарантирует отсутствие дубликатов в пределах одной
сессии продюсера. Пачка публикуется по одному сообщению, и падение процесса в
середине оставит часть пачки опубликованной. Транзакции Kafka сделали бы
публикацию пачки атомарной ценой заметного падения пропускной способности —
оправдано только если частичная пачка реально ломает потребителя.

### Безопасность кластера Kafka

Кластер работает по `PLAINTEXT` в закрытой сети Docker. Для продакшена нужны
SASL/SCRAM, TLS, ACL (сейчас любой клиент внутри сети может писать и читать что
угодно) и шифрование данных на дисках брокеров.

### Геоданные

`ip_hash` не позволяет определить регион, а география — базовый разрез
веб-аналитики. Правильный порядок: определить страну/регион по IP **до**
хеширования и положить в событие только результат (`country`, `region`), а сам
адрес выбросить. Так разрез появляется, а персональные данные не сохраняются.

### Обогащение справочными данными

В событии лежит `target_id` фильма, но не название и жанры; джойн выполняется на
стороне аналитики. Альтернатива — Kafka Streams, сливающий `ugc.clicks.v1` с
топиком каталога. Компромисс: денормализация делает поток самодостаточным, но
фиксирует данные на момент события (переименовали фильм — исторические события
останутся со старым именем). Для аналитики это часто как раз желаемое поведение.

### Эволюция схемы событий

`schema_version` заложена, но процесса миграции нет. Нужно описать: как вводится
`v2` топика, сколько времени потоки живут параллельно, кто отвечает за
дочитывание `v1`.

### Инструменты соблюдения приватности

Для GDPR/152-ФЗ понадобятся: удаление событий пользователя по запросу (в
append-only логе это решается только crypto-shredding — шифрованием на
пользовательском ключе с последующим уничтожением ключа), учёт согласия на сбор,
поддержка `Do Not Track` / `Global Privacy Control` на стороне трекера.

### Локальная буферизация и sticky sessions

Идея «копить события в прослойке и писать в Kafka реже» уже реализована на
уровне продюсера (`linger_ms=20`), а буфер вынесен в Redis — поэтому
синхронизация буферов между инстансами и sticky sessions не нужны. Вопрос
вернётся, если понадобится агрегация *до* Kafka (например, схлопывать серию
«просмотр» в одно событие с длительностью): тогда появится локальное состояние
и привязка клиента к инстансу.
