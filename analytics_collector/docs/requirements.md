# Требования к сервису сбора пользовательских действий

Документ отвечает на первую подзадачу спринта — выявление функциональных и
нефункциональных требований из бизнес-описания.

Исходное бизнес-описание ставит три задачи: отслеживать клики, отслеживать
просмотры страниц и время на них, отслеживать три кастомных события (смена
качества видео, досмотр до конца, использование фильтров поиска). Ниже они
развёрнуты до требований, по которым можно проверить готовую систему.

---

## 1. Функциональные требования

### 1.1. Приём событий

| ID | Требование |
|----|------------|
| FR-1 | Система принимает событие **клика** по элементу интерфейса с указанием типа элемента (фильм, трейлер, категория, жанр, персона, баннер, кнопка, ссылка, пункт меню, результат поиска, рекомендация), идентификатора связанной сущности, URL страницы и позиции элемента в списке. |
| FR-2 | Система принимает событие **просмотра страницы** с указанием типа страницы (главная, фильм, жанр, персона, поиск, промо, профиль, плеер), URL, идентификатора сущности и **времени, проведённого на странице**. |
| FR-3 | Система принимает событие **смены качества видео** с указанием фильма, качества до и после переключения, позиции воспроизведения и признака автоматического переключения. |
| FR-4 | Система принимает событие **просмотра до конца** с указанием фильма, полной длительности и фактически просмотренного времени. Долю просмотра вычисляет сервер. |
| FR-4a | Система принимает **метку прогресса просмотра** (`video_progress`) с указанием фильма, текущей позиции воспроизведения и полной длительности. Долю просмотра вычисляет сервер. Без этих меток невозможно ответить на вопрос «какие фильмы не досматривают»: у брошенного просмотра события FR-4 не существует, и последняя пришедшая метка — единственный признак точки выхода. Поток на два порядка массивнее остальных, поэтому у события отдельный топик. |
| FR-5 | Система принимает событие **использования фильтров поиска** с указанием поискового запроса, списка применённых фильтров (поле + значение) и числа результатов. |
| FR-6 | Любое событие может нести дополнительный плоский словарь произвольных свойств. |
| FR-7 | Система принимает **пачку** разнотипных событий одним запросом (сценарий `navigator.sendBeacon` при уходе со страницы). |

### 1.2. Идентификация пользователя

| ID | Требование |
|----|------------|
| FR-8 | События принимаются как от аутентифицированных, так и от анонимных пользователей. Значительная часть ценного поведения (главная, поиск, промо) происходит до входа. |
| FR-9 | При наличии валидного access-токена событие атрибутируется пользователю: `user_id` берётся **из токена**. |
| FR-10 | Клиент **не может** задать `user_id`, `is_authenticated` и время приёма — эти поля проставляет только сервер. |
| FR-11 | Анонимные события связываются между собой через `anonymous_id` (стабильный идентификатор браузера) и `session_id`. |
| FR-12 | Невалидный, просроченный или отозванный токен не приводит к отказу: событие принимается как анонимное. |

### 1.3. Доставка в Kafka

| ID | Требование |
|----|------------|
| FR-13 | Событие публикуется в топик, соответствующий его типу; имя топика определяется сервером. |
| FR-14 | Ключом партиционирования служит `user_id`, при его отсутствии — `anonymous_id`, затем `session_id`. |
| FR-15 | Сообщение снабжается заголовками: тип события, идентификатор события, версия схемы, `x-request-id`, контекст трассировки. |
| FR-16 | Каждое событие имеет `event_id`; повторная отправка события с тем же `event_id` не создаёт дубликат в топике. |
| FR-17 | Событие обогащается серверными данными: время приёма, тип устройства, ОС и браузер (из User-Agent), хеш IP. |

### 1.4. Эксплуатация

| ID | Требование |
|----|------------|
| FR-18 | Сервис предоставляет пробы живости и готовности, различающие «процесс жив» и «события доставляются без потерь». |
| FR-19 | Сервис экспортирует метрики: принято, опубликовано, буферизовано, потеряно, подавлено дедупликацией; латентность публикации; состояние подключения к брокеру; размер буфера. |
| FR-20 | Сервис предоставляет OpenAPI-документацию по всем ручкам приёма. |

## 2. Нефункциональные требования

### 2.1. Производительность

| ID | Требование | Как проверяется |
|----|------------|-----------------|
| NFR-1 | Латентность приёма одного события: p99 < 50 мс без учёта сети. | Гистограмма `ugc_publish_duration_seconds`. Достигается тем, что ручка не ждёт подтверждения от кворума реплик: публикация возвращает управление после записи в буфер продюсера. **Замер на текущей реализации: 596 из 601 публикаций уложились в 0,5 мс.** |
| NFR-2 | Пропускная способность: не менее 1000 событий/с на инстанс. | Микро-батчинг продюсера (`linger_ms=20`) и сжатие lz4 сокращают число запросов к брокеру на порядок относительно поштучной отправки. |
| NFR-3 | Пакетная отправка снижает число HTTP-запросов от клиента до одного на пачку (до 50 событий). | Ручка `/api/v1/events/batch`. |

### 2.2. Надёжность и доступность

| ID | Требование |
|----|------------|
| NFR-4 | **Сбой инфраструктуры аналитики не приводит к ошибке на клиенте.** Ни недоступность Kafka, ни недоступность Redis, ни недоступность Auth не дают 5xx на ручках приёма. Это прямое следствие требования спринта о том, что сайт не должен ломаться из-за «горячих» зависимостей. |
| NFR-5 | При недоступности Kafka события сохраняются в буфер и доставляются автоматически после восстановления. |
| NFR-6 | Буфер ограничен по размеру: отказ Kafka не должен приводить к исчерпанию памяти Redis, который используется совместно с Auth и Movies API. |
| NFR-7 | Доставка гарантируется на уровне «хотя бы один раз». Дубликаты допустимы и гасятся дедупликацией по `event_id`; потеря события — нет. |
| NFR-8 | Перезапуск сервиса (деплой, OOM, рестарт пода) не теряет события, находящиеся в процессе доставки из буфера. |
| NFR-9 | Кластер Kafka переживает отказ одного брокера без остановки записи и без потери подтверждённых данных (RF=3, `min.insync.replicas=2`, `acks=all`). |
| NFR-10 | Сервис поднимается при недоступной Kafka и самостоятельно восстанавливает подключение. |

### 2.3. Масштабируемость

| ID | Требование |
|----|------------|
| NFR-11 | Инстансы сервиса не хранят состояния: масштабирование горизонтальное, любой запрос обслуживается любым инстансом. Общее состояние (буфер, счётчики лимитов, дедупликация) вынесено в Redis. |
| NFR-12 | Число партиций топика задаёт потолок параллелизма чтения; для массовых потоков (клики, просмотры) их больше, чем для редких. |
| NFR-13 | Потоки событий разных типов масштабируются и настраиваются независимо (отдельные топики). |

### 2.4. Безопасность и приватность

| ID | Требование |
|----|------------|
| NFR-14 | Сырой IP-адрес не попадает ни в Kafka, ни в логи — только необратимый солёный хеш. |
| NFR-15 | Соль хеширования обязательна в продакшене; сервис не стартует со значением по умолчанию. |
| NFR-16 | Размер тела запроса, размер пачки, длины строк и структура пользовательских свойств ограничены. |
| NFR-17 | Все категориальные поля — закрытые перечисления; неизвестные поля в запросе отклоняются. |
| NFR-18 | Имя топика не может быть задано клиентом. |
| NFR-19 | Ограничение частоты запросов действует на уровне Nginx и приложения; пачка расходует лимит пропорционально числу событий в ней. |
| NFR-20 | Процесс в контейнере работает без привилегий root. |
| NFR-21 | Ответы об ошибках не раскрывают внутреннее устройство системы (адреса брокеров, трассировки стека). |
| NFR-22 | Список источников CORS задаётся явно; в продакшене `*` запрещён. |

### 2.5. Наблюдаемость

| ID | Требование |
|----|------------|
| NFR-23 | Каждый запрос имеет сквозной `x-request-id`, доступный в логе Nginx, в логах сервиса, в теге спана и в заголовке сообщения Kafka. |
| NFR-24 | Трассировка не обрывается на границе брокера: спан обработки события консьюмером связывается со спаном HTTP-запроса, в котором оно было принято. |
| NFR-25 | Логи структурированные (JSON), пригодные для машинного сбора. |
| NFR-26 | Потеря события всегда фиксируется отдельной метрикой и записью уровня ERROR. |

### 2.6. Хранение

| ID | Требование |
|----|------------|
| NFR-27 | Сроки хранения задаются на уровне топика и различаются по типам событий: массовые «сырые» потоки — 7 дней, продуктово значимые — 30 дней. Kafka здесь транспорт, а не архив: долговременное хранение — задача аналитической витрины. |

## 3. Границы решения

Сознательно **не** входит в объём этого спринта:

* ~~**Аналитическое хранилище.**~~ Вынесено за границы этого сервиса и **реализовано отдельно**: [`etl_clickhouse/`](../../etl_clickhouse/README.md) переносит поток в ClickHouse, схема хранилища и запросы аналитика — в [`analytics_schema.md`](../../etl_clickhouse/docs/analytics_schema.md).
* **Реестр схем (Schema Registry).** События сериализуются в JSON. Переход на Avro/Protobuf с реестром — следующий шаг, см. `improve_suggestion.md`.
* **Шифрование и авторизация внутри кластера Kafka** (SASL/TLS, ACL). Кластер живёт в закрытой сети Docker.
* **Точно один раз (exactly once)** сквозь всю цепочку. Обеспечивается «хотя бы один раз» плюс дедупликация по `event_id`.
* **Синхронизация буферов между инстансами и sticky sessions** — упомянуты в теории спринта как развитие идеи буферизации; здесь буфер общий (Redis), поэтому синхронизация не нужна.
