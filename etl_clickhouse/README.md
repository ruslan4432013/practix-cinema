# ETL: Kafka → ClickHouse

Непрерывный перенос пользовательских действий из Kafka в аналитическое
хранилище. Поток заканчивался ничем: коллектор писал события в Kafka, но
Kafka — транспорт, а не архив (retention 7–30 дней), и ответить на продуктовые
вопросы было нечем. Этот сервис закрывает конвейер.

```
браузер → analytics-collector → Kafka (6 топиков) → [etl-clickhouse] → ClickHouse
                                                                          ├─ raw_events        сырой поток
                                                                          ├─ film_views        типизированные просмотры
                                                                          ├─ витрины (3 MV)    ответы аналитику
                                                                          └─ invalid_events    карантин
```

Не путать со старым `etl/` в корне репозитория — тот про PostgreSQL →
Elasticsearch и к аналитике отношения не имеет.

## Что умеет

| Требование | Как закрыто |
|---|---|
| Непрерывный перенос | Consumer group на всех шести топиках UGC, включая DLQ |
| Устойчивость к сбою **источника** | Старт при лежащей Kafka, перехват `KafkaError` без падения, `ConsumerRebalanceListener` |
| Устойчивость к сбою **хранилища** | Коммит оффсетов только после успешной вставки + `pause()` партиций на время недоступности |
| Идемпотентность | Три уровня дедупликации (в пачке → `insert_deduplication_token` → `ReplacingMergeTree`) |
| Отравленные сообщения | Карантин `ugc.invalid_events`, конвейер не встаёт |
| Мониторинг памяти | `process_resident_memory_bytes`, `sys.getallocatedblocks()`, `tracemalloc` → `/metrics` + Grafana + алерт |

Подробности: [`docs/reliability.md`](docs/reliability.md) — матрица отказов;
[`docs/analytics_schema.md`](docs/analytics_schema.md) — схема хранилища и
готовые запросы аналитика.

## Устройство

```
ddl/                    схема хранилища (применяет одноразовый clickhouse-init)
scripts/apply_ddl.sh    идемпотентное применение DDL
src/
  main.py               точка входа: порядок запуска и остановки
  core/config.py        настройки (pydantic-settings, UPPER_SNAKE)
  core/logger.py        JSON-логи
  core/metrics.py       реестр Prometheus + коллекторы процесса
  core/memory.py        MemoryWatcher: RSS, живые блоки CPython, tracemalloc
  core/backoff.py       асинхронная экспоненциальная пауза с джиттером
  brokers/consumer.py   фабрика AIOKafkaConsumer и устойчивый старт
  brokers/rebalance.py  флаш и коммит до отдачи партиций
  transform/            конверт → строки таблиц
  sinks/clickhouse.py   вставка, настройки идемпотентности, классификация отказов
  pipeline/buffer.py    единственное место, где данные лежат в памяти
  pipeline/runner.py    цикл чтение → вставка → коммит, pause/resume
  pipeline/reporters.py фоновые замеры лага и здоровья приёмника
  observability/http.py эндпоинт /metrics
```

Импорты идут от корня `src` (`from core.config import ...`), как в
`analytics_collector/` и `auth/`.

## Ключевые решения

**Оффсеты коммитятся только после вставки.** Порядок «вставил → прокоммитил»
неразрывен: падение между шагами приводит к повторной вставке, которую гасит
дедупликация. Обратный порядок дал бы потерю. Это осознанный at-least-once
поверх недостижимого exactly-once.

**Backpressure вместо очереди в памяти.** Пока ClickHouse недоступен, чтение из
Kafka ставится на паузу, и в куче живёт ровно одна пачка. Копить непрокоммиченные
пачки в списке значило бы превратить часовой простой хранилища в OOM-kill —
и всё равно перечитывать из Kafka с последнего коммита. Роль неограниченного
буфера играет сама Kafka: там данные реплицированы, лежат на диске и переживают
перезапуск.

**Холостой `getmany` в цикле ретраев.** `pause()` не продлевает
`max_poll_interval_ms` — aiokafka отсчитывает интервал от последнего `getmany`.
Без холостого опроса группа исключила бы консьюмера ровно во время аварии,
которую он пережидает.

**`distributed_foreground_insert=1`.** По умолчанию вставка в Distributed
асинхронная: сервер отвечает «ок», положив данные в спул-каталог координатора.
Прокоммитив оффсеты по такому «ок», мы потеряли бы данные при падении узла.

## Запуск

Отдельно сервис не запускают — он поднимается вместе со стеком:

```bash
docker compose up -d --build          # из корня репозитория
docker compose logs -f etl-clickhouse
curl -s http://localhost:9101/metrics | grep process_resident_memory_bytes
```

Локально, без Docker (нужны доступные Kafka и ClickHouse):

```bash
cd etl_clickhouse
pip install -r requirements.txt
PYTHONPATH=src python -m main
```

## Тесты

```bash
docker compose -f tests/functional/docker-compose.yml \
               --project-directory tests/functional run --rm --build etl-tests
```

23 функциональных теста: доставка всех семейств событий, идемпотентность,
карантин отравленных сообщений, витрины (оба вопроса задания), метрики памяти и
отдельно — **отказ хранилища**: тест проверяет не «сервис выжил», а что оффсеты
в Kafka не сдвинулись, пока ClickHouse лежал.

Тестовый стенд — один узел ClickHouse со встроенным Keeper, и к нему
применяются **те же самые** файлы `ddl/*.sql`, что и к боевому кластеру.

## Конфигурация

Полный список переменных с комментариями — в `.env.example` (сервисном и
корневом). Что стоит знать в первую очередь:

| Переменная | Зачем |
|---|---|
| `ETL_FLUSH_INTERVAL` | Верхняя граница задержки данных при слабом трафике |
| `ETL_MAX_PARTITION_FETCH_BYTES`, `ETL_FETCH_MAX_BYTES` | Реальные рычаги потребления памяти, а не `ETL_BATCH_MAX_ROWS` |
| `CH_INSERT_QUORUM` | 2 — отказ реплики становится лагом; 0 — окном потери |
| `ETL_TRACEMALLOC_ENABLED` | Включать на время расследования утечки |
| `ETL_MAX_SCHEMA_VERSION` | Защита от тихого разбора конверта новой версии |
| `OTEL_TRACES_SAMPLER_RATIO` | Доля трассируемых трейсов; без сэмплирования спаны сами станут нагрузкой |

## Трассировка

Коллектор кладёт `traceparent` в заголовки сообщений Kafka;
`AIOKafkaInstrumentor` восстанавливает контекст на этой стороне, а вставка пачки
оборачивается собственным спаном `etl.flush` с атрибутами причины закрытия
пачки, числа строк и объёма. Так цепочка «браузер → коллектор → Kafka →
ClickHouse» видна в Jaeger целиком.

Спан ставится **на пачку, а не на сообщение**: сообщений десятки тысяч в
секунду, и спан на каждое сам стал бы нагрузкой. По той же причине включён
`ParentBased(TraceIdRatioBased(0.01))` — решение о сэмплировании принимается по
`trace_id`, поэтому оно согласовано с решением коллектора, и трейс либо целиком
попадает в выборку, либо целиком нет.

## Что дальше

Осознанные упрощения, принятые в объёме спринта. Ничто из перечисленного не
мешает сервису работать.

### Exactly-once вместо at-least-once

Оффсеты хранятся в Kafka, вставка идемпотентна по `insert_deduplication_token` и
`ReplacingMergeTree`. Но дедупликация третьего уровня отложенная, поэтому
аналитик обязан помнить про `uniq`/`FINAL`. Правило легко забыть, и ошибка будет
тихой.

Решение — хранить оффсеты в самом ClickHouse и вставлять их одной транзакцией с
данными (таблица `ugc.etl_offsets`, чтение при `on_partitions_assigned`, `seek()`
на сохранённую позицию). Тогда повторная вставка становится невозможной, а не
гасимой.

### Kafka Connect с ClickHouse Sink вместо своего кода

Свой консьюмер на aiokafka — это код, который уже написан и оттестирован
сообществом. Стоит оценить `clickhouse-kafka-connect`: он умеет ровно этот
сценарий, включая идемпотентность по состоянию в Keeper. Против — потеря
контроля над трансформацией (`view_id`, `progress_pct` пришлось бы считать в
материализованном представлении) и появление ещё одного кластера в стеке
(Connect). Решение неочевидно, поэтому оставлено как задача с исследованием.

### Обогащение справочником фильмов

В хранилище лежит только `film_id`, и любой отчёт требует джойна с PostgreSQL
вручную, за пределами ClickHouse. Словарь (`CREATE DICTIONARY`) поверх
`theatre-db` с названием, жанрами и годом, обновляемый по `LIFETIME`, превратил
бы «топ фильмов» из списка UUID в читаемый человеком результат.

### Тип `JSON` вместо `String` для payload

Сейчас `payload String CODEC(ZSTD(3))`, разбор через `JSONExtract*` — каждый
запрос по полю внутри payload означает полный разбор строки. Нативный тип `JSON`
(стабилен с 25.x) хранит подполя колоночно и даёт индексы по ним. Требует
проверки на реальном объёме: динамические подколонки могут дать взрывной рост
числа файлов.

### Проекции и `SAMPLE BY`

Витрины покрывают известные вопросы, ad-hoc идёт по детальным данным.
`PROJECTION` для частых срезов по `device_type`/`os` и
`SAMPLE BY cityHash64(view_id)` в `film_views` ускорили бы прикидочные запросы
по большому объёму.

### Горизонтальное масштабирование ETL

Сейчас один контейнер; параллелизм даётся партициями, но потолок — один процесс.
Код готов к нескольким репликам в одной consumer group
(`ConsumerRebalanceListener`, идемпотентная вставка), но это не проверено под
нагрузкой: нужен тест на ребаланс-шторм и подбор `ETL_MAX_POLL_INTERVAL_MS` под
реальное время вставки.

### Ретеншен и холодное хранение

Сейчас `TTL ... DELETE`: 6 месяцев для сырых данных, 24 для просмотров. Сырой
поток годичной давности нужен редко, но его потеря необратима — правильнее
`TTL ... TO VOLUME 'cold'` с S3-диском вместо удаления.
