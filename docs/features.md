## Спринт 2: интеграция Auth и observability

### 1. Интеграция Auth + graceful degradation

Auth — «горячая» зависимость, поэтому вся интеграция построена так, чтобы сайт **не падал при недоступности Auth**. Используемые паттерны: retry с экспоненциальным backoff, circuit breaker, fallback / partial results.

- **Movies API** локально валидирует JWT (общий `authjwt_secret_key`) **и** делает живую межсервисную проверку прав `POST http://auth:8000/api/v1/users/check-permissions`. Роли кэшируются в Redis (`user:{id}:roles`, TTL 300 с). Проверка защищена **circuit breaker'ом на Redis** (`auth:cb:failures`, порог отказов + окно сброса) и короткими таймаутами (`auth_request_timeout = 2.0 с`) — если Auth недоступен, детали фильмов деградируют мягко, без жёсткого отказа.
- **Django Admin** — кастомный `AuthServiceBackend` аутентифицирует пользователя через Auth (`/api/v1/auth/login`, затем `/api/v1/users/me`), маппит роли Auth → `is_staff` / `is_superuser`, использует ограниченный retry + экспоненциальный backoff и таймауты, а при недоступности Auth **откатывается на локальный `ModelBackend`**.

### 2. Распределённая трассировка → Jaeger

Все три app-сервиса (auth / api / django) экспортируют OpenTelemetry-спаны по OTLP/HTTP в `http://jaeger:4318/v1/traces` (включается флагом `OTEL_ENABLED`). Инструментированы FastAPI + httpx (и Django + requests), поэтому `traceparent` пробрасывается сквозь межсервисные вызовы.

Корреляция через **X-Request-Id**: Nginx генерирует/перезаписывает его (`$request_id`, защита от подмены), каждый сервис требует заголовок (400, если отсутствует), проставляет его в активный спан, возвращает в ответе и пробрасывает в исходящие межсервисные вызовы. Трейсы доступны в UI: **http://localhost:16686**.

### 2а. Сбор ошибок → GlitchTip (Sentry-совместимый)

Jaeger отвечает на вопрос «где ушло время», Prometheus — «сколько и как часто», и ни один из них не отвечает на «что именно упало и с каким стеком». Эту дыру закрывает сбор ошибок: все двенадцать сервисов шлют необработанные исключения и `ERROR`-логи в один приёмник через **официальный `sentry-sdk`**.

**Почему GlitchTip, а не self-hosted Sentry.** Официальная сборка Sentry требует 16 ГБ RAM + 16 ГБ swap, 4 ядра и ~40 контейнеров (Kafka, ClickHouse, Snuba, Relay, Symbolicator). Стенд уже просит ≥12 ГБ на профиле `warehouse`. GlitchTip реализует тот же протокол приёма событий и работает с тем же SDK без единой правки в коде, стоя три контейнера и ~512 МБ. Переезд на sentry.io или на настоящий Sentry — замена `SENTRY_DSN` и ничего больше.

**Sentry ловит ошибки, трассировку ведёт Jaeger.** `traces_sample_rate` не передаётся намеренно: OTel-интеграция SDK ставит свой глобальный `TracerProvider` и тихо увела бы спаны из Jaeger. Связь между системами — тегами: в каждое событие проставляются `service`, `request_id` и `trace_id` активного спана, поэтому из ошибки в GlitchTip можно перейти в конкретный трейс Jaeger и в строки лога. Инвариант закреплён тестом `libs/platform-core/tests/test_sentry.py::test_init_does_not_replace_global_tracer_provider`.

Общий механизм — `practix_core.sentry.init_sentry()` (extra `practix-core[sentry]`); `django-admin` за границей своего `uv.lock` инициализирует SDK сам в `example/wsgi.py`. Чувствительные поля вырезаются `EventScrubber`'ом: к штатному списку добавлены `authjwt_secret_key`, `ugc_ip_hash_salt`, `ch_password` и токены — в кадрах стека едут локальные переменные, и при падении внутри логина там лежал бы пароль.

**Первый запуск** (DSN появляется только после создания проекта):

```bash
docker compose --env-file .env -f infra/compose/docker-compose.yml \
               --project-directory infra/compose --profile observability up -d
```

1. открыть **http://localhost:8001**, зарегистрироваться, создать организацию и проект (платформа — Python);
2. скопировать выданный DSN в `SENTRY_DSN` в корневом `.env`, выставить `SENTRY_ENABLED=true`;
3. перезапустить прикладные сервисы — события пойдут в приёмник.

### 2б. Логи → ELK

Логи всех сервисов собираются в один индекс и ищутся по одному `request_id`. Раньше они жили только в docker-драйвере `json-file`: разбросаны по трём десяткам контейнеров, теряются при пересоздании контейнера, не фильтруются по сервису.

**Конвейер:** приложение пишет JSON в `stdout` → docker кладёт строку в `json-file` → **Filebeat** читает файл → **Logstash** разбирает → **Elasticsearch** (`practix-logs-YYYY.MM.DD`) → **Kibana**.

**Приложения о существовании ELK не знают** — намеренно. Драйвер `gelf` был бы проще, но шлёт по UDP без подтверждения (перезапуск Logstash теряет записи молча) и ломает `docker compose logs`. Прямая отправка из кода (`python-logstash`) жёстко привязала бы каждый сервис к получателю логов.

**Единый формат.** Одна строка JSON с фиксированным набором и порядком ключей: `timestamp`, `level`, `logger`, `message`, `request_id`, `service` — плюс всё, что передано через `extra=...`. Имя сервиса берётся из `OTEL_SERVICE_NAME`, того же, которым подписаны трассировка и сбор ошибок, поэтому из ошибки в GlitchTip можно перейти в трейс Jaeger, а из трейса — в строки лога. Access-лог nginx использует тот же набор ключей (`log_format json_access`), и один запрос `request_id: "…"` находит и его строку, и строки приложения.

Порядок ключей — не косметика: по первому ключу (`timestamp`) Logstash отличает наши строки от чужого JSON. Postgres, Kafka, Jaeger и Elasticsearch тоже пишут JSON, но свой — с полем `service` в виде объекта и `status` в виде строки, — и раскладывать его на те же поля значит ломать общий индекс. Их строки хранятся целиком в `message`.

```bash
docker compose --env-file .env -f infra/compose/docker-compose.yml \
               --project-directory infra/compose --profile logging up -d
```

Затем в **http://localhost:5601** создать data view `practix-logs-*` с полем времени `@timestamp` (Management → Stack Management → Data Views) и открыть Discover. Примеры KQL: `service: "nginx" and status >= 500`, `request_id: "…"`, `service: "auth-service" and level: "ERROR"`.

Устройство конвейера, две ловушки (петля обратной связи и контейнеры чужих проектов на той же машине), разбор проблем и вопрос ретеншена — в **[`infra/elk/README.md`](../infra/elk/README.md)**.

### 3. Rate limiting

Auth-сервис применяет **fixed-window** ограничитель на Redis (`RateLimitMiddleware`), настраиваемый через `RATE_LIMIT_ENABLED` / `RATE_LIMIT_TIMES` (по умолчанию 20) / `RATE_LIMIT_SECONDS` (по умолчанию 60).

### 4. Вход через соцсети (Yandex OAuth) + отвязка

Функциональность включается флагом `OAUTH_ENABLED`. Эндпоинты под `/api/v1/oauth`:

- `GET /yandex/login` — редирект на Yandex, CSRF-`state` хранится в Redis.
- `GET /yandex/callback` — валидация `state`, обмен `code`, выпуск наших JWT.
- Новые/существующие пользователи связываются через таблицу `social_accounts`; OAuth-only пользователи создаются без пароля (passwordless).
- `GET /social/accounts` — список привязанных аккаунтов.
- `DELETE /social/accounts/{account_id}` — отвязать аккаунт (блокируется с **409**, если это оставит passwordless-пользователя без способа входа).

Настройки: `YANDEX_CLIENT_ID` / `YANDEX_CLIENT_SECRET` / `YANDEX_REDIRECT_URI`.

### 5. Партиционирование таблиц

Таблица `login_history` партиционирована **в два уровня**: RANGE по `auth_date` (по годам) → LIST по `device_type` (`web` / `mobile` / `smart` + default). Тип устройства определяется по `User-Agent` при входе. Смысл: на миллионах строк это даёт отсечение по временному диапазону для запросов истории плюс разделение по классам устройств.

## Спринт 3: сбор пользовательских действий (UGC)

Сервис [`apps/analytics-collector/`](../apps/analytics-collector/README.md) — аналог Яндекс.Метрики для кинотеатра. Принимает клики, просмотры страниц (с временем на них) и кастомные события (смена качества видео, досмотр до конца, использование фильтров поиска) и публикует их в Kafka.

**Топики** — по одному на семейство событий (стратегия «топик на тип сущности»): `ugc.clicks.v1`, `ugc.page_views.v1`, `ugc.video_events.v1`, `ugc.video_progress.v1`, `ugc.search_events.v1` плюс `ugc.events.dlq.v1`. Все с RF=3 и `min.insync.replicas=2`, создаются одноразовой задачей `kafka-init`. **Ключ партиционирования** — `user_id` (для анонимов `anonymous_id` → `session_id`): сохраняет порядок событий одного пользователя и даёт равномерное распределение.

**Graceful degradation.** Приём событий не ломается ни от чего: при недоступной Kafka событие уходит в ограниченный по длине буфер Redis (`202 {"status":"buffered"}`), а фоновый дренаж доставляет накопленное после восстановления. Дренаж крашоустойчив — записи извлекаются через `LMOVE` в in-flight-список и удаляются только после подтверждения брокером, поэтому перезапуск сервиса с непустым буфером ничего не теряет. Недоступность Redis отключает rate limit и дедупликацию (fail-open), но 5xx клиент не получает никогда.

**Безопасность.** `user_id` берётся только из подписи JWT — во входных моделях такого поля нет вовсе, и `extra='forbid'` превращает попытку его передать в 422. Сырой IP не покидает процесс: в Kafka уходит солёный `blake2b`. Ограничены размер тела (отсекается до чтения), размер пачки, длины строк и структура `properties`. Имя топика недоступно клиенту.

**Отличия от Auth и Movies API — осознанные:** `X-Request-Id` здесь *генерируется*, а не требуется (400 сломал бы `navigator.sendBeacon`, который не умеет ставить заголовки); лимит частоты выше и учитывает вес пачки; документация висит на `/api/analytics/openapi`, потому что `/api/openapi` за Nginx уже занят Movies API.

Подробнее: [требования](../apps/analytics-collector/docs/requirements.md) · [архитектура и диаграммы](../apps/analytics-collector/docs/architecture.md) · [топики](../apps/analytics-collector/docs/kafka_topics.md) · [клиентский трекер](../apps/analytics-collector/docs/client_snippet.md).

## Спринт 4: аналитическое хранилище и ETL

Поток событий заканчивался ничем: Kafka — транспорт, а не архив (retention
7–30 дней), и ответить на продуктовые вопросы было нечем. Сервис
[`apps/etl-clickhouse/`](../apps/etl-clickhouse/README.md) непрерывно переносит события в
ClickHouse и закрывает конвейер.

### Хранилище

**Кластер 2 шарда × 2 реплики** плюс кворум `ClickHouse Keeper` из трёх узлов.
Шардирование даёт масштаб, репликация — переживание отказа узла; одно без
другого бессмысленно. Keeper именно кворумный: при одном узле его падение
останавливает все вставки в реплицируемые таблицы и любой `ON CLUSTER`-DDL, и
«две реплики на шард» перестают что-либо значить.

Схема (DDL в `apps/etl-clickhouse/ddl/`, применяет одноразовый `clickhouse-init`):

| Таблица | Что содержит |
|---|---|
| `ugc.raw_events` | Сырой поток всех шести семейств событий; `payload` — как есть |
| `ugc.film_views` | Типизированные просмотры: `view_id`, `completion_rate`, `progress_pct` |
| `ugc.film_views_daily` | Витрина: **самые просматриваемые фильмы** |
| `ugc.film_retention_daily` | Витрина: **кривая досмотра — где именно бросают** |
| `ugc.film_completion_daily` | Витрина: доля брошенных просмотров, квантили досмотра |
| `ugc.invalid_events` | Карантин нераспознанных сообщений |

### Новое событие `video_progress`

Ответить на вопрос «какие фильмы не досматривают» по существующим событиям было
невозможно: `video_completed` приходит только у тех, кто **досмотрел**, а у
брошенного просмотра события просто нет. Поэтому добавлена периодическая метка
прогресса — последний увиденный бакет и есть точка выхода зрителя.

У неё **отдельный топик** `ugc.video_progress.v1` (12 партиций, retention 7
дней): при тике раз в 30 секунд двухчасовой фильм даёт ~240 событий на просмотр
против одного `video_completed`, и в общем топике этот firehose задавил бы
редкие, но ценные события плеера.

### Устойчивость к сбоям

**Источник.** Сервис поднимается при лежащей Kafka, переживает её пропажу в
работе и закрывает пачку до отдачи партиций при ребалансе.

**Хранилище.** Оффсеты коммитятся **только** после успешной вставки, а на время
недоступности ClickHouse чтение из Kafka ставится на паузу — в куче живёт ровно
одна пачка. Роль неограниченного буфера играет сама Kafka: там данные
реплицированы, лежат на диске и переживают перезапуск. Копить непрокоммиченные
пачки в памяти значило бы превратить часовой простой хранилища в OOM-kill — и
всё равно перечитывать с последнего коммита.

**Идемпотентность** — три уровня: `set` по `event_id` внутри пачки →
`insert_deduplication_token` из диапазонов оффсетов → `ReplacingMergeTree`.
Третий уровень отложенный, поэтому все витрины считают `uniq`, а не `count`.

**Отравленные сообщения** не блокируют конвейер: битый JSON, неизвестный тип
события или конверт более новой версии уезжают в `ugc.invalid_events`, а оффсет
коммитится вместе с пачкой.

Проверка отказоустойчивости руками — в [быстром старте](quickstart.md#проверка-отказоустойчивости-etl).

### Мониторинг памяти

Поток непрерывный, поэтому важна не разовая цифра, а форма кривой: RSS обязан
выходить на плато. ETL отдаёт на `:9101/metrics` три независимых показателя —
`process_resident_memory_bytes` (RSS глазами ОС), `etl_ch_allocated_blocks`
(живые блоки CPython, не зависят от поведения аллокатора) и метрики
`tracemalloc` (за флагом `ETL_TRACEMALLOC_ENABLED`, топ-10 мест роста — в логи).
Prometheus собирает их вместе с метриками коллектора и всех узлов ClickHouse,
Grafana рисует дашборд «UGC ETL → ClickHouse», алерт `EtlMemoryGrowth` срабатывает
на устойчиво положительную производную RSS за три часа.

Подробнее: [ETL](../apps/etl-clickhouse/README.md) · [схема хранилища и запросы аналитика](../apps/etl-clickhouse/docs/analytics_schema.md) · [матрица отказов](../apps/etl-clickhouse/docs/reliability.md).

## Спринт 5: исследование хранилища под UGC (лайки, рецензии, закладки)

Пользовательский контент в проекте пока не хранится нигде: коллектор принимает
события и отдаёт их в Kafka, состоянием он не владеет, и прочитать «сколько у
фильма лайков» из него нельзя в принципе.

`research/ugc-storage/` — воспроизводимый стенд, на котором три кандидата
(MongoDB, PostgreSQL, ClickHouse) меряются на одинаковом датасете класса S
(10 млн лайков, 1 млн закладок, 500 тыс. рецензий) по реальным сценариям чтения
и по времени появления только что поставленной оценки. Там же — обоснование
выбранной схемы данных и разбор вопроса «отдельный сервис или расширение
существующего».

Результат: на объёме S требование 200 мс проходят все три кандидата, поэтому
выбор сделан по цене владения — взят **PostgreSQL**, который в проекте уже есть.
Самое дорогое место оказалось не в выборе базы, а в схеме: преагрегат рейтинга
фильма даёт разницу в 50 раз на популярных фильмах.

**Почему не MongoDB.** Задание называет её кандидатом («сравнить MongoDB и,
например, Postgres»), и сравнение проведено честно — на живом шардированном
кластере из десяти контейнеров. Итог однозначен: **MongoDB проигрывает
PostgreSQL по p99 во всех одиннадцати сценариях** — от 2.9× на списке
понравившихся фильмов до 169× на рецензиях, отсортированных по полезности
(152.3 против 0.9 мс). Взять её после
таких замеров значило бы выбрать хранилище по названию в задании, а не по
данным. Работа по MongoDB не выброшена: кластер, схема, ключи шардирования и
найденная ошибка с покрывающим индексом в шардированной коллекции описаны в
исследовании и составляют готовый план перехода на тот день, когда данные
перестанут помещаться на один узел PostgreSQL.

Стенд запускается отдельным `docker compose` со своими профилями и портами и с
боевым стеком не пересекается.

Подробнее: [исследование, стенд и результаты замеров](../research/ugc-storage/README.md).

## Спринт 6: сервис пользовательского контента

Исследование спринта 5 закончилось выводом «нужен отдельный сервис» —
`apps/ugc-api/` его реализует. Оценки фильмов (целое 0..10, где лайк и дизлайк —
частные случаи 10 и 0), закладки «посмотреть позже», рецензии с гибкой
сортировкой и голосованием за полезность. Своя база `ugc-db`, своя миграция,
своя точка документации `/api/ugc/openapi`.

Два решения, которые определяют облик сервиса:

* **Ответ означает сохранение.** В отличие от коллектора, где ingest-ручка
  никогда не отдаёт 5xx, здесь оценка и преагрегат пишутся одной транзакцией, а
  перед ней берётся advisory-блокировка по паре (пользователь, фильм) — иначе
  двойной клик даёт пользователю две оценки на одном фильме.
* **Преагрегат вместо агрегации на лету.** Разница на популярном фильме — 13 раз
  на PostgreSQL, и это единственное место, где 200 мс могли не выдержать.
  Лайки и дизлайки не хранятся, а выводятся из гистограммы оценок по настраиваемому
  порогу: смена порога — правка переменной, а не пересчёт десяти миллионов строк.

Подробнее: [сервис, схема и контракт](../apps/ugc-api/README.md).

## Спринт 7: сервис нотификаций и панель рассылок

`apps/notifications/` — админ-панель, в которой менеджер создаёт сообщение
пользователям, выбирает способ доставки и отправляет его сразу, через N часов или
по расписанию («каждую пятницу», «каждый Новый год»), плюс CRUD шаблонов
сообщений. И весь тракт, без которого кнопка «Отправить» была бы враньём:
RabbitMQ, воркер сборки писем, воркер отправки, планировщик, SMTP.

Решения, определяющие облик сервиса:

* **Кнопка не отправляет письма.** Она пишет прогон и строку в транзакционный
  outbox — в одной транзакции — и возвращает управление менеджеру мгновенно,
  сколько бы адресов ни было в сегменте. Публикацию, разворачивание аудитории и
  SMTP делают отдельные процессы. Между `COMMIT` и `basic_publish` иначе остаётся
  окно, в котором рассылка исчезает: по данным запущена, по факту не существует.
* **Три уникальных ограничения вместо аккуратности.** `run_key` не даёт слоту
  расписания сработать дважды (в том числе после простоя генератора и из двух
  реплик планировщика), `idempotency_key` не даёт повторной доставке из брокера
  стать вторым письмом, outbox не даёт сообщению потеряться.
* **Возможности шаблонизатора урезаны, а не задокументированы.** Глобалы Jinja2
  очищены: без `range` в шаблоне нечего итерировать, кроме переменных из белого
  списка, — «вечный цикл», которым пугает теория, становится недостижимым.
  Сохранение проходит три проверки: синтаксис, доступные возможности, рендерится ли.
* **Django внутри uv-workspace на Python 3.13.** `django-admin` вынесен наружу
  из-за сборки uwsgi и держит три форка `practix-core`; здесь взят gunicorn,
  зависимость чисто питоновская, и логгер, Sentry и трассировка импортируются, а
  не копируются. Дублирование по репозиторию — 0.65 % при пороге 0.8 %.
* **Фиксированные события приходят от чужих сервисов по HTTP, а не публикацией
  в брокер.** Auth после регистрации и контентная админка после появления фильма
  шлют заявку в приём нотификаций фоновой задачей с повторами; продюсер не знает
  ни про exchange, ни про routing key. Это и есть «API — центральный узел»: он
  принимает заявку и кладёт её в очередь. Продюсер по построению повторяет
  запрос, поэтому дедупликация сделана по ПРИРОДНОМУ ключу (`user_id`, `film_id`),
  а не по `event_id`: продюсер, перегенерировавший UUID на повторе, иначе отправил
  бы второе приветственное письмо. Какое событие какой рассылкой отвечать —
  редактируемая строка в базе, а не константа в образе.
* **Воркеров два, и к воркеру не приходят личные данные.** Веер публикует в
  очередь ТОЛЬКО идентификаторы получателей; имя, фамилию и адрес формирующий
  воркер запрашивает у Auth сам (`POST /api/v1/users/lookup`, пачкой, с паузой и
  кешем) и собирает персональное письмо, а отправляющий занят одним SMTP —
  коннект к почтовому серверу стоит около пяти секунд и держится открытым, в нём
  нельзя простаивать в ожидании HTTP. При недоступности Auth вся пачка уходит в
  свой ярус парковочной очереди: письмо на десять минут позже лучше письма без
  имени. Адрес, скопированный в очередь заранее, к моменту отправки мог уже
  принадлежать другому человеку — поэтому он и не копируется.
* **Личный кабинет читает проекцию, а не журнал.** Запись в ленте появляется в
  момент доставки и хранит тему с превью, но не тело письма: сто тысяч получателей
  иначе дали бы сто тысяч копий одного HTML. Токен проверяется локально общим
  секретом, а отзыв — в Redis сервиса Auth, там же, где он пишется; при
  недоступности Redis ручка закрывается, а не открывается.

* **Уведомление доходит, даже когда websocket отвалился.** Теория предлагает
  комбинировать подходы ради изящной деградации — здесь их три ступени: сокет
  (`apps/notifications-ws/`), long polling на том же шлюзе и лента кабинета,
  единственная долговечная. Шлюз не хранит ничего, поэтому его падение не теряет
  уведомлений: клиент при каждой смене транспорта догоняет ленту по `since` и
  склеивает её с кадрами по `task_id`. Токен на handshake не передаётся вовсе —
  вместо него одноразовый ticket, который гаснет при первом использовании, а
  живое соединение периодически перепроверяется по денилисту Auth, поэтому выход
  из системы закрывает открытые вкладки.

Подробнее: [проектное решение](notifications.md) ·
[websocket-шлюз](websockets.md) ·
[сервис и эксплуатация](../apps/notifications/README.md) ·
[шлюз](../apps/notifications-ws/README.md).

## Спринт 8: короткие ссылки и подтверждение email

Последний незакрытый пункт чек-листа десятого спринта — **сервис сокращения
ссылок** ([`apps/link-shortener/`](../apps/link-shortener/README.md)) — и та
задача, ради которой он существует: welcome-письмо со ссылкой подтверждения
адреса.

* **Короткий код — непрозрачный ключ, а не сумка параметров.** Задание требует,
  чтобы ссылка «включала» идентификатор пользователя, срок действия и
  `redirectUrl`. Здесь это колонки строки, к которым код и резолвится — ровно в
  том смысле, в каком `bit.ly/b8NwYzA` «включает» целевой адрес. Класть их в URL
  параметрами значило бы получить строку в две сотни символов, то есть отменить
  сокращение, ради которого задание и заведено. Проверяемость даёт ручка
  интроспекции: все три поля одним запросом.
* **Код случайный, а не порядковый.** Счётчик в base62 дал бы коды короче и без
  коллизий — и сделал бы ссылки перечислимыми. Эта ссылка не рекламная: переход
  по ней ПОДТВЕРЖДАЕТ адрес электронной почты, и перебор соседних кодов стал бы
  способом подтвердить чужой ящик.
* **Просроченная, отозванная и несуществующая ссылки отвечают одинаково.**
  Задание требует 404 на просроченной; различать её от несуществующей означало
  бы подсказывать перебирающему, какие коды есть. А вот недоступность Auth — это
  **503 с `Retry-After`**, а не 404: ссылка жива, не работает система, и 404
  сказал бы человеку «выбросьте её».
* **302, а не 301.** 301 кэшируется навсегда: браузер перестал бы ходить в
  сервис, отозванная ссылка продолжала бы уводить из кэша (прямое противоречие
  требованию про 404), смена `redirectUrl` в панели не повлияла бы на уже
  разосланные письма, а визиты по закэшированному редиректу не считались бы.
* **Флагом владеет Auth, ссылку выпускает воркер рассылки.** Шортенер в чужую
  базу не пишет — он зовёт `POST /api/v1/users/{id}/confirm-email` под учёткой с
  УЗКОЙ ролью `email-confirmer`. Ссылку выпускает сборщик письма, а не Auth при
  регистрации: регистрация не должна получать зависимость от второго сервиса,
  Auth не знает про `redirectUrl` из чужой панели, а срок жизни ссылки обязан
  начинаться от сборки — письмо, отложенное тихими часами, иначе приезжало бы
  уже протухшим.
* **`redirectUrl` настраивается в панели** — валидируемым полем кампании, а не
  ключом в JSON-контексте, где опечатка `redirectUrl` вместо `redirect_url` не
  падает, а просто ничего не делает.
* **Ссылка выпускается только тем, кому нужна.** Сборщик идёт в шортенер, лишь
  если снапшот прогона просит `{{ confirm_url }}`: безусловный выпуск оставил бы
  строку на каждого получателя любой массовой рассылки.
* **Подтверждение идемпотентно, потому что по ссылке ходят дважды** — человек и
  сканер ссылок его почтового клиента, причём сканер первым. Повтор возвращает
  `200 already_confirmed`, а не 409: у вызывающего должен быть один путь успеха.
* **Открытый редирект закрыт на записи, а не на чтении.** К моменту перехода
  ссылка уже в чьём-то ящике. Белый список хостов ловит и `//evil.com`
  (protocol-relative), и `http://localhost@evil.com` (userinfo).
* **Сервис в ядре compose, без профиля.** Ссылка обязана открываться как
  `http://localhost/s/AbC1234`, значит её маршрутизирует nginx, а тот резолвит
  upstream'ы на старте. Профиль со своим хост-портом дал бы
  `http://localhost:8092/s/AbC1234` — длиннее того адреса, который сокращаем.

Подробнее: [сервис и эксплуатация](../apps/link-shortener/README.md).

## Дипломный трек: рекомендательная система

Два сервиса вместо одного: [`apps/recsys-trainer/`](../apps/recsys-trainer/README.md)
— офлайн-обучение в профиле `warehouse`, и
[`apps/recommendations-api/`](../apps/recommendations-api/README.md) — выдача в
ядре, за nginx. Похожие фильмы, персональные подборки, популярное; своя витрина
`recs-db`, свой горячий слой `redis-recs`.

* **Батч думает, выдача читает.** Бюджет ответа — 300 мс, а коллаборативная
  фильтрация в момент запроса это перемножение матриц на сотнях тысяч строк.
  Поэтому система разрезана надвое, и шов — витрина топ-N. Пока меняется модель,
  а не контракт витрины, изменение не трогает ни API, ни nginx, ни фронт: именно
  это свойство позволяло резать ALS целиком, не переделывая остальное.
* **Версия батча входит в первичный ключ каждой таблицы списков.** Отсюда сразу
  два системных требования, и не обещанием, а построением: повторный прогон
  физически не может удвоить строки (он пишет в другое место, а не аккуратно
  делает `ON CONFLICT`), а выдача, прочитавшая номер версии один раз за запрос,
  видит целостный батч, а не половину нового поверх половины старого. Указатель
  на текущую версию — ровно одна строка по построению схемы
  (`id boolean PRIMARY KEY CHECK (id)`), а не по договорённости «всегда пишем
  `WHERE id = 1`».
* **Схемой витрины владеет ВЫДАЧА, хотя пишет в неё батч.** Контейнер миграций
  переиспользует образ сервиса, а выдача живёт в ядре и поднимается всегда, тогда
  как батч сидит в профиле `warehouse`. Батч пишет сырым SQL — второй копии
  моделей в репозитории нет.
* **Отказ не имеет права стать 5xx на странице фильма** — и одной лестницы
  деградации для этого мало. На живом стенде выяснилось, что отказ бывает не
  ошибкой, а **молчанием**: остановленный контейнер не отвечает отказом, его
  адрес исчезает из сети, исключения не возникает, `except` не выполняется, и
  лестница просто не доходит до следующей ступени. Поэтому у каждого источника
  есть таймаут, у всего обработчика — общий срок `RECS_REQUEST_BUDGET` (меньше
  `proxy_read_timeout` nginx), а у кэша — предохранитель `RECS_CACHE_FUSE_SECONDS`:
  без него два таймаута молчащего Redis съедали бюджет раньше, чем очередь
  доходила до PostgreSQL, то есть отказ **ускорителя** отменял работу **источника
  истины**.
* **404 отдаётся, только когда отсутствие фильма доказано** — непустой снимок
  каталога, в котором его нет. Наивная проверка превращала в 404 весь каталог
  разом, стоило указателю в кэше пережить свою версию: в несуществующей версии
  нет ни одного фильма по построению. «Не знаю» — это не «нет».
* **Ответ всегда называет свой источник** (`similar` / `personal` / `popular`).
  При подмене персональной выдачи популярной код остаётся 200, и без этого поля
  авария неотличима от здоровья.
* **Версия в ключе кэша вместо инвалидации.** Массовое удаление ключей означало
  бы, что между `DEL` и прогревом весь трафик проваливается в PostgreSQL —
  плановая операция сама себе создаёт пик, причём ровно того размера, от которого
  кэш и защищает. Переключение — это смена одного указателя, старое уходит по TTL;
  прогрев идёт после коммита, указатель ставится последним.
* **Просмотренное исключает батч, а не библиотека.** У `implicit` есть флаг
  `filter_already_liked_items`, но он не держит слова: когда неотфильтрованных
  кандидатов меньше запрошенного `N`, библиотека добивает выдачу уже
  просмотренными позициями — то есть бьёт ровно по активным зрителям. Фильтр
  продублирован явно, поведение библиотеки закреплено юнит-тестом.
* **Генератор синтетики — часть поставки, а не костыль.** Стенд поднимается с
  пустым ClickHouse, и «данных мало для обучения» числится риском номер один.
  Фильмы берутся настоящие из каталога (выдуманные UUID дали бы рекомендации на
  фильмы, которых нет), зрители разбиты на вкусовые кластеры — при равномерно
  случайных просмотрах со-встречаемость выродилась бы в шум, и метрики показали
  бы правду о генераторе, а не о модели. Два слива: `--sink clickhouse` даёт
  объём, `--sink api` проверяет живучесть стыка — и уже поймал расхождение
  словаря качества видео с коллектором.
* **Обучение — долгоживущий процесс, а не cron.** Одноразовый экспортирует
  метрики только пока работает, Prometheus не застаёт его почти никогда, и
  «обучение не запускалось третьи сутки» выглядело бы точно так же, как «всё
  хорошо». Гейджи витрины заполняются из самой витрины, а не из результата
  последнего прогона.
* **Качество измерено против baseline «просто популярное»** на выборке,
  отложенной **по времени** (случайный сплит разрешил бы модели учиться на том,
  что человек посмотрит завтра): со-встречаемость — precision@10 0.0527 и
  покрытие каталога 84 %, ALS — 0.0471 и 85 %, baseline — 0.0048 и 1 %. Обе
  модели обгоняют baseline примерно на порядок по точности и на два по покрытию.
  Числа получены на синтетике и говорят о конвейере, а не о вкусах живой
  аудитории.

Подробнее: [устройство и решения](recommendations.md) ·
[выдача](../apps/recommendations-api/README.md) ·
[обучение](../apps/recsys-trainer/README.md).
