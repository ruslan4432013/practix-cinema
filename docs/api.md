# Ключевые эндпоинты

Полные контракты — в Swagger каждого сервиса: Movies API `/api/openapi`,
Analytics Collector `/api/analytics/openapi`, UGC API `/api/ugc/openapi`,
Auth — `/api/openapi` его контейнера.

## Movies API — `/api/v1`

| Метод | URL | Описание |
|-------|-----|----------|
| GET | `/api/v1/films` | Список фильмов (сортировка, фильтр по жанру) |
| GET | `/api/v1/films/search` | Полнотекстовый поиск фильмов |
| GET | `/api/v1/films/{id}` | Детальная карточка (детали гейтятся подпиской через Auth) |

| GET | `/api/v1/persons/{id}` | Персона с фильмографией |

### Users — `/api/v1/users`

| Метод | URL | Описание |
|-------|-----|----------|
| GET | `/me` | Текущий пользователь |
| PATCH | `/me/credentials` | Изменение логина/email (с подтверждением паролем) |
| PATCH | `/me/profile` | Изменение имени и фамилии — без пароля: отображаемое имя не учётные данные |
| GET | `` | Постраничный список пользователей, только admin — синхронизация витрины нотификаций |
| POST | `/lookup` | Личные данные пачкой по списку id (≤500), только admin. Ответ: `{items, missing}`. Этим воркер рассылки персонифицирует письмо: из очереди к нему приходит только `user_id` |
| POST | `/check-permissions` | Межсервисная проверка прав |
| POST | `/{user_id}/confirm-email` | Пометить адрес подтверждённым. Роль `email-confirmer` (УЗКАЯ, не admin). Зовётся сервисом сокращения ссылок при переходе по короткой ссылке из welcome-письма. Идемпотентна: повтор — `200 already_confirmed`, а не 409, потому что до человека по ссылке ходит сканер почтового клиента |

`UserResponse` несёт `email_verified` — по нему сегментируется будущая рассылка «напомнить о подтверждении». Смена email через `/me/credentials` **сбрасывает флаг**: подтверждён был старый адрес.

`POST`, а не `GET ?ids=`: 500 UUID — около 20 КБ строки запроса при лимите
заголовков в 8–16 КБ. `missing` перечисляется явно, чтобы вызывающий отличал
удалённого пользователя от неверного идентификатора.

`first_name` и `last_name` необязательны, принимаются при регистрации и
возвращаются во всех ответах с пользователем; у заведённых раньше они `null`.

## Analytics Collector — `/api/v1/events` (аутентификация опциональна)

| Метод | URL | Описание |
|-------|-----|----------|

## UGC API — `/api/v1/{likes,ratings,bookmarks,reviews}`

| Метод | URL | Описание |
|-------|-----|----------|
| PUT · DELETE | `/likes/{film_id}` | Поставить/изменить и снять оценку 0..10 |
| GET | `/likes/me` | Понравившиеся фильмы пользователя |
| GET | `/ratings/{film_id}` | Рейтинг фильма: среднее, гистограмма, лайки и дизлайки по порогу |
| PUT · DELETE | `/bookmarks/{film_id}` | Закладка «посмотреть позже», идемпотентно |
| GET | `/bookmarks` | Закладки пользователя |
| POST | `/reviews` | Написать рецензию (одна на фильм от пользователя) |
| GET | `/reviews?film_id=…&sort=new\|useful\|rating` | Рецензии фильма в трёх порядках |

Запись требует токена; `user_id` берётся только из подписи и в теле запроса
запрещён. Swagger — на `/api/ugc/openapi`.

## Нотификации — `/api/v1/notifications` (профиль `notifications`)

| Метод | URL | Описание |
|-------|-----|----------|
| POST | `/events` | Фиксированное событие проекта (`type`) **или** запуск существующей рассылки (`campaign_id`). Заголовок `X-Internal-Token` — межсервисный секрет |
| POST | `/messages` | Сообщение в свободном формате конкретному пользователю. Тот же секрет |
| GET | `/unsubscribe/{token}` | Отписка по подписанной ссылке из письма |
| GET | `/me/messages?limit=&offset=` | Лента уведомлений пользователя. `Authorization: Bearer <access>` |
| POST | `/me/messages/{id}/read` | Отметить уведомление прочитанным |
| GET | `/health/live` · `/health/ready` | Пробы: живость без зависимостей, готовность с проверкой базы и размера outbox |

Swagger у сервиса нет: интерфейс менеджера — это Django admin на `/admin/`.

**`POST /events`.** Две формы тела различаются наличием `type`. Фиксированное
событие: `{"type": "user.registered", "event_id": …, "occurred_at": …, "data": {…}}`;
поддерживаются `user.registered` (нужны `user_id`, `email`) и `film.published`
(нужны `film_id`, `title`). Исходная форма `{"campaign_id": …}` работает как
раньше. Какая рассылка отвечает на событие, задаёт менеджер в панели
(«Привязки событий»), а не настройки.

**Коды ответа — это контракт с циклом ретраев продюсера**, и различать их
обязательно: `202` принято (`run_id`); `200 duplicate` — повтор того же события,
делать больше нечего; `200 ignored` (`no_binding` / `binding_disabled` /
`unknown_subscriber` / `email_conflict`) — заявка принята и осознанно ни к чему не
привела, повтор не поможет; `400` — ошибка вызывающего; `401` — не тот секрет;
`404` — несуществующая рассылка; `409` — рассылка отменена или её шаблон выключен.
**Повторять осмысленно только `5xx` и обрыв связи**: продюсер, ретраящий всё
не-2xx, будет вечно долбиться в выключенную привязку.

**`POST /messages`.** `{"event_id", "user_id", "type": "email|sms|push", …}`.
Внимание: здесь `type` — это КАНАЛ, а в `/events` — имя события; поэтому ручки и
разные. Текст задаётся либо `template_id` (код шаблона из панели), либо парой
`subject`/`text` — взаимоисключающе. Сырой текст валидируется как шаблон прямо на
приёме и при ошибке даёт `400` со списком `errors`. `event_id` обязателен: это
ключ дедупликации, природного ключа у прямого сообщения нет. Нереализованный канал
(`sms`, `push`) принимается с `202` и оседает в журнале как `channel_unavailable`.
Категорию письма передать нельзя — она берётся из рассылки, иначе вызывающий мог
бы поставить `transactional` и пройти мимо любой отписки.

**`GET /me/messages`.** Отдаёт `{items, total, limit, offset}` — та же форма, что
у `GET /api/v1/users` в Auth. Идентификатор берётся только из subject токена и
никогда из запроса. Токен проверяется локально общим секретом, отзыв — в Redis
сервиса Auth; при его недоступности ручка закрывается (`401`), а не открывается.
В ленте лежат тема и превью, но не тело письма.

Панель и пользовательские ручки не за nginx — они публикуются прямым портом
(`NOTIFICATIONS_HOST_PORT`, по умолчанию 8090); почему — в `docs/notifications.md`.

### Websocket-шлюз (порт 8091, профиль `notifications`)

| Метод | Путь | Назначение |
|---|---|---|
| `POST` | `/api/v1/ws/ticket` | Одноразовый ticket + политика деградации (`Authorization: Bearer`) |
| `WS` | `/api/v1/ws?ticket=…` | Поток уведомлений |
| `GET` | `/api/v1/ws/poll?wait=25` | Long polling — ступень деградации (`Authorization: Bearer`) |

Токен на handshake не передаётся: браузер не умеет ставить заголовки в
`new WebSocket()`, а JWT в query-строке навсегда оседает в access-логах. Третья и
единственная ДОЛГОВЕЧНАЯ ступень деградации — лента кабинета выше
(`?since=` для догона, `task_id` для склейки). Разбор — `docs/websockets.md`.

## Сокращение ссылок — `/s/{code}` и `/api/v1/links`

| Метод | Путь | Назначение |
|---|---|---|
| `GET`/`HEAD` | `/s/{code}` | Публичный переход. **302** + `Cache-Control: no-store`. Нет кода / просрочен / отозван → **страница 404** (три случая склеены намеренно: разные ответы — оракул для перебора). `kind=confirm_email` перед редиректом зовёт Auth; его недоступность → **503 + `Retry-After`**, а не 404 |
| `POST` | `/api/v1/links` | Создать ссылку. Межсервисная, `Authorization: Bearer <SHORTENER_INTERNAL_TOKEN>`. **Маршрута в nginx нет** — недостижима снаружи по построению. Повтор с тем же `idempotency_key` → `200` и ТА ЖЕ ссылка |
| `GET` | `/api/v1/links/{code}` | Интроспекция: `user_id`, `expires_at`, `target_url`, `visit_count`. Существует затем, чтобы требование «ссылка включает эти три вещи» было проверяемым |
| — | `/api/shortener/openapi` | Документация (`/api/openapi`, `/api/analytics`, `/api/ugc` заняты) |

**302, а не 301.** 301 кэшируется навсегда: отозванная ссылка продолжала бы
уводить из кэша (противоречие требованию «просроченная → 404»), смена
`redirectUrl` в панели не влияла бы на разосланные письма, а визиты по
закэшированному редиректу не считались бы. Разбор — `apps/link-shortener/README.md`.
