# Конфигурация (переменные окружения)

Корневой `.env` (шаблон — `.env.example`) драйвит все сервисы compose. Ключевые группы:

| Группа | Переменные |
|--------|-----------|
| **Rate limit** (Auth) | `RATE_LIMIT_ENABLED`, `RATE_LIMIT_TIMES` (20), `RATE_LIMIT_SECONDS` (60), `AUTH_TRUSTED_PROXIES` — сети, из которых принимаются `X-Real-IP` / `X-Forwarded-For`. Без него лимит не работает вовсе: заголовок от недоверенного адреса подделывается, и клиент получал бы новый счётчик на каждый запрос. Значение совпадает с `UGC_TRUSTED_PROXIES` коллектора — оба сервиса стоят за одним nginx; пустая строка отключает проверку и нужна только тестам, где приложение поднято in-process |
| **Трассировка** | `OTEL_ENABLED`, `OTEL_EXPORTER_OTLP_ENDPOINT=http://jaeger:4318` (per-service `OTEL_SERVICE_NAME` задаётся в compose) |
| **Сбор ошибок** | `SENTRY_ENABLED`, `SENTRY_DSN`, `SENTRY_ENVIRONMENT`, `SENTRY_RELEASE`, `SENTRY_SAMPLE_RATE`, `SENTRY_SEND_DEFAULT_PII`. Один DSN на все сервисы, различает их тег `service` (берётся из `OTEL_SERVICE_NAME`) |
| **GlitchTip** | `GLITCHTIP_SECRET_KEY` (**обязательно заменить**), `GLITCHTIP_DOMAIN`, `GLITCHTIP_HOST_PORT`, `GLITCHTIP_ENABLE_OPEN_USER_REGISTRATION`, `GLITCHTIP_POSTGRES_*`, `GLITCHTIP_EMAIL_URL` |
| **Логи** | `LOG_LEVEL`, `LOG_JSON` (все сервисы). ELK: `ELASTIC_LOGS_HOST_PORT` (9210), `KIBANA_HOST_PORT` (5601), `LOGSTASH_BEATS_HOST_PORT` (5044), `ES_LOGS_JAVA_OPTS`, `LS_JAVA_OPTS`, `KIBANA_ENCRYPTION_KEY`, `COMPOSE_PROJECT_NAME` (по нему Filebeat отсеивает контейнеры чужих проектов) |
| **Интеграция Auth** (Movies API / Django) | `AUTHJWT_SECRET_KEY`, `AUTH_API_URL=http://auth:8000`, `AUTH_REQUEST_TIMEOUT` / `AUTH_API_TIMEOUT=2.0`, `AUTH_API_MAX_ATTEMPTS=3`. `AUTHJWT_DENYLIST_ENABLED` / `AUTHJWT_DENYLIST_TOKEN_CHECKS` (по умолчанию только `access`) читают все, кто проверяет токен локально, — Auth, коллектор, `ugc-api`, выдача рекомендаций, websocket-шлюз; денилист при этом всегда лежит в ЯДРОВОМ `redis` (`AUTH_REDIS_*`, база 0), там же, где его пишет Auth. Ключи включают саму проверку и выбирают вид токена, но НЕ задают поведение при недоступном денилисте: это решение сервиса, а не стенда, и у каждого оно своё (`raise` у Auth — он владеет отзывом, `allow` у коллектора, `deny` у `ugc-api` и рекомендаций; у нотификаций и шлюза для него есть свои ключи `NOTIFY_DENYLIST_ON_ERROR` / `NOTIFY_WS_DENYLIST_ON_ERROR`) |
| **OAuth** | `OAUTH_ENABLED=False`, `YANDEX_CLIENT_ID`, `YANDEX_CLIENT_SECRET`, `YANDEX_REDIRECT_URI=http://localhost/api/v1/oauth/yandex/callback` |
| **PostgreSQL (фильмы)** | `POSTGRES_HOST` / `POSTGRES_DB` / `POSTGRES_USER` / `POSTGRES_PASSWORD` |
| **PostgreSQL (Auth)** | `AUTH_POSTGRES_HOST` / `AUTH_POSTGRES_PORT` / `AUTH_POSTGRES_DB` / `AUTH_POSTGRES_USER` / `AUTH_POSTGRES_PASSWORD` |
| **Auth: собственные настройки** (`apps/auth/`) | Ключи БЕЗ значений по умолчанию: пропущенный роняет сервис `ValidationError`'ом ещё на импорте, и это сделано намеренно — секрет по умолчанию опасен именно тем, что работает. Раньше они жили в отдельном `auth/.env.example` и попадали в образ вместе с `COPY auth/ .`; после перехода на один Dockerfile в образ копируется корневой шаблон, поэтому место им здесь. `AUTHJWT_SECRET_KEY` (**обязательно заменить** — им подписывает Auth, а проверяют локально Movies API, коллектор, `ugc-api`, рекомендации, нотификации и websocket-шлюз), `ACCESS_TOKEN_EXPIRES` / `REFRESH_TOKEN_EXPIRES` — время жизни токенов **в секундах**, и они же TTL записей денилиста: отозванный JTI хранится ровно столько, сколько токен мог бы прожить, иначе Redis копил бы мусор вечно. `AUTHJWT_DENYLIST_ENABLED` / `AUTHJWT_DENYLIST_TOKEN_CHECKS` (у Auth, в отличие от читателей, проверяются **оба** вида токена: он владеет отзывом, и refresh обязан отзываться при ротации), `DEFAULT_ROLE_NAME` (роль, выдаваемая при регистрации и при первом входе через OAuth) / `SUPERUSER_ROLES` (роли с обходом проверки прав; читаются из claim'а токена, а не из базы). `AUTH_POSTGRES_*` — своя база, строкой выше. `JWT_SECRET_KEY` / `JWT_ALGORITHM` / `ACCESS_TOKEN_EXPIRE_MINUTES` / `REFRESH_TOKEN_EXPIRE_DAYS` / `BASE_DIR` тоже обязательны, но кодом не читаются — не путать `ACCESS_TOKEN_EXPIRE_MINUTES` с действующим `ACCESS_TOKEN_EXPIRES` (правка первого не меняет ничего) |
| **Elasticsearch / Redis** | `ELASTIC_HOST` / `ELASTIC_PORT`, `REDIS_HOST` / `REDIS_PORT` |
| **Django superuser** | `DJANGO_SUPERUSER_USERNAME` / `DJANGO_SUPERUSER_PASSWORD` / `DJANGO_SUPERUSER_EMAIL` |
| **Kafka** | `KAFKA_CLUSTER_ID` (одинаковый у всех узлов), `KAFKA_BOOTSTRAP_SERVERS`, `KAFKA_TOPIC_*` |
| **Analytics Collector** | `UGC_ENV` (`prod` включает обязательные проверки безопасности), `UGC_REDIS_DB=1`, `UGC_FALLBACK_*` (буфер деградации), `UGC_MAX_BODY_BYTES` / `UGC_MAX_BATCH_SIZE`, `UGC_RATE_LIMIT_*` (600/60 с), `UGC_IP_HASH_SALT` (**обязательно заменить в проде**), `UGC_CORS_ALLOW_ORIGINS` |
| **ClickHouse** | `CH_CLUSTER=ugc_cluster`, `CH_DATABASE=ugc`, `CH_USER` / `CH_PASSWORD` (**обязательно заменить в проде**), `CH_HOSTS` (по одному узлу на шард — это координаторы вставки, а не реплики), `CH_INSERT_QUORUM=2` (аналог acks=all + ISR=2: отказ реплики становится лагом, а не потерей), `CH_RETRY_*`, `CH_SEND_RECEIVE_TIMEOUT` |
| **ETL ClickHouse** | `ETL_CONSUMER_GROUP`, `ETL_FLUSH_INTERVAL` / `ETL_BATCH_MAX_ROWS` / `ETL_BATCH_MAX_BYTES` (три порога закрытия пачки), `ETL_FETCH_MAX_BYTES` / `ETL_MAX_PARTITION_FETCH_BYTES` (**реальные рычаги потребления памяти**), `ETL_MAX_SCHEMA_VERSION`, `ETL_METRICS_PORT`, `ETL_TRACEMALLOC_*`, `ETL_RSS_WARN_MB` |
| **Grafana** | `GF_SECURITY_ADMIN_PASSWORD` |
| **UGC API** (`apps/ugc-api/`) | `UGC_API_*` — префикс свой, и это не многословие: голый `UGC_` принадлежит `analytics-collector` (строка выше, около двадцати пяти ключей), а корневой `.env` читают оба контейнера, поэтому совпадение имени означало бы одну переменную на два разных сервиса. `UGC_API_ENV` (`prod` запрещает старт со значениями по умолчанию — они опасны не слабостью, а тем, что работают), `UGC_API_POSTGRES_*` — своя база `ugc-db`, а не таблицы в каталоге: чтений здесь на порядок больше записей, и этот профиль нагрузки не должен доставать ни фильмы, ни вход в систему; **`UGC_API_DB_POOL_SIZE` / `UGC_API_DB_MAX_OVERFLOW`** (потолок считается НА КОНТЕЙНЕР: пул принадлежит воркеру, а воркеров четыре, поэтому база видит `4 × (pool + overflow)`. Прежние 10 + 20 давали 120 против `max_connections` = 100 — под нагрузкой оценка и закладка получали бы `too many connections` вместо ответа; теперь 5 + 5 → 40, и в бюджет `ugc-db` помещаются ещё батч рекомендаций, который читает отсюда оценки (≤ 15), пересчёт преагрегата и миграции. Сходимость закреплена `apps/ugc-api/tests/unit/test_connection_budget.py`, который читает `--workers` из Dockerfile и `max_connections` из compose) / `UGC_API_DB_ECHO` (выключен: построчный лог SQL на каждый запрос стоит дороже самих запросов — в Auth он включён и в проде, здесь эту ошибку не повторяем); **`UGC_API_LIKE_THRESHOLD`** — оценка, с которой начинается лайк. Ключ ПРОДУКТОВЫЙ, и он же причина, по которой рейтинг фильма хранится гистограммой из 11 чисел, а не парой счётчиков «лайки/дизлайки»: смена порога — правка этой строки, а не пересчёт десяти миллионов оценок. Порог возвращается в ответе, чтобы клиент не разошёлся с сервером в том, что считать лайком; `UGC_API_LIKED_MIN_RATING` (граница выборки «понравившиеся фильмы» — те же 8, на которых мерился сценарий R1 исследования) / `UGC_API_REVIEW_MAX_LENGTH`; `AUTHJWT_SECRET_KEY` + `AUTHJWT_DENYLIST_*` + `AUTH_REDIS_*` — токен проверяется ЛОКАЛЬНО, без сетевого вызова в Auth, а денилист читается в ядровом `redis`; политика при его недоступности — `deny`, строже коллекторского `allow`: принять запись по отозванному токену хуже, чем отказать в ней, и `/health/ready` в этом состоянии отвечает `degraded`. `UGC_API_REDIS_TIMEOUT` — единственный ключ этого блока с префиксом, и это не небрежность: имена вокруг описывают ЧУЖОЙ экземпляр Redis и обязаны совпадать у всех читателей одного `.env`, а таймаут — настройка нашего клиента (голый `UGC_REDIS_TIMEOUT` тоже занят коллектором). `SUPERUSER_ROLES` — кому позволено удалять чужие рецензии. Ключей частоты запросов здесь нет намеренно: запись ограничена зоной `ugc_write` (20 r/s) в nginx, а третий форкнутый лимитер не прошёл бы гейт дублирования |
| **Рекомендации: витрина и выдача** (`apps/recommendations-api/`) | `RECS_*`. Префикс описывает **ВИТРИНУ**, и те же самые ключи читает батч `recsys-trainer`: витрина одна, и второй набор на то же соединение — это ровно тот способ, которым конфигурация молча расходится с реальностью. `RECS_ENV`, `RECS_POSTGRES_*` (своя база), **`RECS_DB_POOL_SIZE` / `RECS_DB_MAX_OVERFLOW`** (потолок считается НА КОНТЕЙНЕР: пул принадлежит воркеру, а воркеров четыре, поэтому база видит `4 × (pool + overflow)`. Прежние 10 + 20 давали 120 против `max_connections` = 100 у `recs-db` — под нагрузкой `too many connections` вместо ответа; теперь 5 + 5 → 40, а лимит базы задан у неё явно, чтобы обе половины арифметики было с чем сверить. Сходимость закреплена `apps/recommendations-api/tests/unit/test_connection_budget.py`, который читает `--workers` из Dockerfile и `max_connections` из compose) / **`RECS_DB_TIMEOUT`** (обязательный, а не тюнинг: остановленная база не даёт отказа, а даёт ожидание, и ступень «витрина недоступна → популярное» без него не срабатывает); `RECS_REDIS_*` — ОТДЕЛЬНЫЙ экземпляр под горячий слой, не база в общем `redis`, где `volatile-lru` делит память с сессиями Auth; `RECS_CACHE_TTL` (TTL ключей версии — именно он убирает старую версию после переключения указателя: массового удаления ключей нет, оно само себе создавало бы пик промахов) / `RECS_POINTER_TTL` (сколько держать номер версии в памяти процесса) / **`RECS_CACHE_FUSE_SECONDS`** (предохранитель: после первой неудачи Redis не трогаем несколько секунд, иначе два таймаута молчащего контейнера съедают бюджет раньше, чем очередь дойдёт до PostgreSQL — отказ ускорителя отменял бы работу источника истины); **`RECS_REQUEST_BUDGET`** (жёсткий срок на весь ответ, заведомо меньше `proxy_read_timeout` маршрута в nginx — без него пользователь получает 504 вместо 200 с популярным); `RECS_DEFAULT_LIMIT` / `RECS_MAX_LIMIT` (потолок обрезает `limit`, а не отвергает его 422); `RECS_ENRICH_*` / `RECS_MOVIES_API_*` (необязательное обогащение названиями — каталог принадлежит Movies API); `RECS_AUTH_REDIS_TIMEOUT` (денилист читается в ЯДРОВОМ `redis`, там же, где его пишет Auth; политика при недоступности — `deny`), `RECS_METRICS_ENABLED` |
| **Рекомендации: обучение** (`apps/recsys-trainer/`) | `RECS_TRAINER_*` — только батч; чужие источники читаются существующими ключами и здесь не переизобретаются (ClickHouse — `CH_*`, каталог — `POSTGRES_*`, оценки — `UGC_API_POSTGRES_*`). `RECS_TRAINER_MIN_COMPLETION` (ниже этой доли просмотра взаимодействие не считается сигналом) / `RECS_TRAINER_MIN_USER_EVENTS` / `RECS_TRAINER_MIN_FILM_EVENTS`, `RECS_TRAINER_TOP_N` / `RECS_TRAINER_POPULAR_LIMIT` / `RECS_TRAINER_POPULAR_WINDOW_DAYS`, `RECS_TRAINER_MAX_INTERACTIONS` / `RECS_TRAINER_MAX_PERSONAL_USERS`, `RECS_TRAINER_RATINGS_ENABLED`; `RECS_TRAINER_ALS_*` (**`ALS_ENABLED` выключает эпик одним флагом** — витрина обязана оставаться рабочей без персональной выдачи; `ALS_ALPHA` — та самая alpha из Hu-Koren-Volinsky, где ноль означает «не знаю», а не «не нравится»); `RECS_TRAINER_WRITE_BATCH` / `RECS_TRAINER_KEEP_VERSIONS` / `RECS_TRAINER_WARMUP_FILMS`; `RECS_TRAINER_INTERVAL_SECONDS` (сутки: вкусы за ночь не меняются, а суточный цикл даёт запас на повтор) / `RECS_TRAINER_RUN_ON_START` (без него стенд после подъёма ждал бы сутки до первой рекомендации; лишний тик безопасен — `run_key` уникален); `RECS_TRAINER_METRICS_*` / `RECS_TRAINER_DATA_DIR` / `RECS_TRAINER_COLLECTOR_URL` / `RECS_TRAINER_GENERATOR_SEED` (генератор синтетики — часть поставки: стенд поднимается с пустым ClickHouse) |
| **Нотификации** | `NOTIFY_ENV`, `NOTIFY_SECRET_KEY` / `NOTIFY_DEBUG` / `NOTIFY_ALLOWED_HOSTS` / `NOTIFY_CSRF_TRUSTED_ORIGINS`, `NOTIFY_POSTGRES_*` (своя база), `NOTIFY_AMQP_URL` / `NOTIFY_AMQP_HEARTBEAT` (больше самой долгой блокирующей операции воркера — иначе канал рвётся посреди отправки) / `NOTIFY_AMQP_SOCKET_TIMEOUT` / `NOTIFY_AMQP_STACK_TIMEOUT` (дедлайн ПОДКЛЮЧЕНИЯ, не путать с heartbeat: без него ожидание TCP отмеряет ядро, а планировщик однопоточный — за публикацией стоят тик расписаний, чистки и веер) / `NOTIFY_PREFETCH_COUNT` / `NOTIFY_RETRY_TTL_MS` / `NOTIFY_MAX_ATTEMPTS`, `NOTIFY_SMTP_*` (включая `NOTIFY_SMTP_RATE_PER_SECOND` — темп, которым не роняют почтовый сервер, / `NOTIFY_SMTP_RATE_SCOPE` — этот темп считается НА СЕРВИС через общий слот в Redis ядра, потому что попроцессный лимит умножался бы на число реплик отправляющего воркера; проверяется на старте) / `NOTIFY_OUTBOX_RETRY_START` / `NOTIFY_OUTBOX_RETRY_MAX` (отсрочка после неудачной публикации: без неё бюджет попыток мерил не выносливость, а секунды — слив крутится раз в секунду) / `NOTIFY_OUTBOX_ALERT_PENDING` (порог, после которого `/health/ready` отвечает `degraded`) / `NOTIFY_ATTEMPTS_RETENTION_DAYS` (журнал попыток чистится тем же часовым тиком, что и лента) / `NOTIFY_REPORT_TTL_MS` (срок жизни отчётного события — задан НА СООБЩЕНИИ, потому что очередь без консьюмера уже объявлена и новые аргументы дали бы 406), `NOTIFY_QUIET_HOURS_*` (в таймзоне получателя; | **Websocket-шлюз** (`apps/notifications-ws/`) | `NOTIFY_WS_*` (префикс свой: голый `NOTIFY_` принадлежит панели и воркерам, а корневой `.env` читают все сразу). `NOTIFY_WS_TICKET_TTL` — срок жизни одноразового ticket'а; `NOTIFY_WS_ALLOWED_ORIGINS` — единственный барьер против CSWSH, потому что у websocket нет same-origin policy; `NOTIFY_WS_REVALIDATE_SECONDS` — период перепроверки отзыва (без него сокет пережил бы logout); `NOTIFY_WS_RECONNECT_*` и `NOTIFY_WS_PROBE_INTERVAL` — политика деградации, которую шлюз ОБЪЯВЛЯЕТ клиенту вместе с ticket'ом, чтобы тайминги фронтенда не были зашиты в JavaScript. Без префикса, потому что описывают чужие сущности: `AUTHJWT_SECRET_KEY`, `AUTH_REDIS_*`, `NOTIFY_AMQP_URL` |
| **Сокращение ссылок** (`apps/link-shortener/`) | `SHORTENER_*` (префикс свой: `UGC_`, `UGC_API_`, `NOTIFY_`, `NOTIFY_WS_`, `ETL_` и `CH_` заняты, а корневой `.env` читают все контейнеры). `SHORTENER_POSTGRES_*` — своя база; **`SHORTENER_DB_POOL_SIZE` / `SHORTENER_DB_MAX_OVERFLOW`** (потолок считается НА КОНТЕЙНЕР: пул принадлежит воркеру, а воркеров четыре, поэтому база видит `4 × (pool + overflow)`. Прежние 10 + 20 давали 120 против умолчания postgres в 100, и отказ пришёл бы в пик — сразу после массовой рассылки, — а человек прочитал бы его как «ссылка из письма не работает»; теперь 5 + 5 → 40, а лимит `shortener-db` задан у неё явно, чтобы обе половины арифметики было с чем сверить. Сходимость закреплена `apps/link-shortener/tests/unit/test_connection_budget.py`); `SHORTENER_PUBLIC_BASE_URL` / `SHORTENER_REDIRECT_PATH` — ВНЕШНИЙ адрес ссылки (она уезжает в письмо и открывается с телефона), путь обязан совпадать с `location ^~ /s/` в nginx; `SHORTENER_CODE_LENGTH` (7 — 62⁷ вариантов: короче нельзя, ссылка подтверждает адрес почты и перечислимый код означал бы подтверждение чужого ящика перебором) / `SHORTENER_CODE_MAX_ATTEMPTS`; `SHORTENER_DEFAULT_TTL_HOURS` / `SHORTENER_MAX_TTL_HOURS`; **`SHORTENER_ALLOWED_REDIRECT_HOSTS`** — белый список хостов редиректа, единственная защита от открытого редиректа (пустое значение = фишинг с нашим доменом в адресной строке жертвы); `SHORTENER_INTERNAL_TOKEN` (**обязательно заменить**) — служебный токен ручки создания ссылок; `SHORTENER_AUTH_*` — учётка с УЗКОЙ ролью `email-confirmer`, которой сервис помечает адрес подтверждённым; `SHORTENER_PURGE_BATCH` / `SHORTENER_PURGE_SLEEP` — размер пачки и пауза между пачками у `cli purge`: уборка удаляет протухшие строки порциями, потому что один DELETE на всю таблицу — это длинная транзакция, держащая блокировки на строках, по которым в это же время идёт счётчик визитов горячего редиректа (и разом раздувающая WAL) |
| **Ссылка подтверждения в письме** (нотификации) | `NOTIFY_SHORTENER_API_URL`, `NOTIFY_SHORTENER_INTERNAL_TOKEN` (**та же строка, что `SHORTENER_INTERNAL_TOKEN`** — две стороны одного секрета), `NOTIFY_SHORTENER_TIMEOUT` / `NOTIFY_SHORTENER_MAX_ATTEMPTS`, `NOTIFY_CONFIRM_REDIRECT_URL` (запасное значение, когда поле кампании пусто; по умолчанию главная страница кинотеатра), `NOTIFY_CONFIRM_LINK_TTL_HOURS` (отсчитывается от СБОРКИ письма, а не от регистрации — иначе письмо, отложенное тихими часами, приезжало бы с мёртвой ссылкой) |
| **Продюсеры событий** (Auth, контентная админка) | `NOTIFY_EVENTS_ENABLED` (**выключено по умолчанию**: без профиля `notifications` такого хоста нет в сети, и включённый продюсер резолвил бы его на каждой регистрации), `NOTIFY_API_URL`, `NOTIFY_INTAKE_TOKEN` (тот же секрет и то же имя, что у нотификаций — ротация в одном месте), `NOTIFY_EVENT_TIMEOUT` / `NOTIFY_EVENT_MAX_ATTEMPTS` (повторы только на 5xx и на обрыве; провал доставки события никогда не ломает регистрацию или сохранение фильма) |

Все публикуемые порты — тоже переменные (`NGINX_HOST_PORT`, `JAEGER_UI_HOST_PORT`
и прочие), поэтому адреса из [быстрого старта](quickstart.md) меняются вместе с
ними. Состав хранилищ и портов по умолчанию — в [`architecture.md`](architecture.md).
