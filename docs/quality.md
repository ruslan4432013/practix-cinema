# Качество кода, проверки целостности и CI

Единый конфиг `ruff` (линтер + форматтер) на весь монорепозиторий — в
`pyproject.toml`. Версии инструментов закреплены в ОДНОМ месте,
`[dependency-groups] dev` того же файла: раньше версия `ruff` была пришпилена в
двух местах (CI и pre-commit), а в самом репозитории — нигде.

```bash
uv run ruff check . && uv run ruff format .   # напрямую
npx nx run-many -t lint                        # то же, по проектам, с кешем
npx nx affected -t lint typecheck test         # только затронутое
pre-commit install                             # те же проверки перед коммитом
```

## Два линтера, и это не дублирование

`ruff` — **гейт**: красный ломает сборку, поэтому набор правил подобран так,
чтобы каждое срабатывание было обязательным к исправлению.

`wemake-python-styleguide` (`.flake8`, версия — там же, в `[dependency-groups]
dev`) — **советник**: он на порядок строже (сложность, вложенность, магические
числа, длина тела `try`), и на существующем коде даёт ~1900 замечаний. Включить
его гейтом означало бы либо переписать репозиторий в один заход, либо утопить
конфиг в `noqa` — то есть выключить его же. Поэтому он не блокирует мерж, а
попадает в HTML-отчёт (ниже), где его вывод читается как список долга и
сравнивается между прогонами.

Из `.flake8` не отключено ничего «ради зелёного отчёта»: там только `E501` (за
длину строки отвечает форматтер) и `WPS` на тестах, которые по своей природе
нарушают половину правил. Отдельная ловушка: `flake8` **молча игнорирует**
неизвестные ключи конфига, поэтому строки про кавычки (`Q000`) и RST-докстринги
из конфига убраны — в WPS 1.x этих плагинов нет в составе, и записи о них
настраивали несуществующие правила. Перед добавлением строки в конфиг стоит
убедиться, что код вообще срабатывает:

```bash
uv run flake8 --format='%(code)s' apps libs tools | sort | uniq -c | sort -rn
```

`mypy` включён на все библиотеки `libs/` и проходит строго. Приложения
подключаются по одному отдельными задачами: конфиг `mypy` существовал и раньше,
но не запускался ни в CI, ни в pre-commit, и под ним накопилось 10 ошибок типов.
Поэтому сейчас он вызывается в трёх местах — `uv run mypy` вручную, хук
`pre-commit` и отдельный шаг CI по корневому конфигу (а не только
`nx affected -t typecheck`, который при правке вне библиотек не выбирает
ничего и проходит пустым).

## Дублирование кода

Гейт против регресса — `jscpd`, порог в `.jscpd.json`:

```bash
npm run dup
```

Порог держится чуть выше фактического уровня и снижается по мере извлечения
общего кода (5 % → 0.8 % за время переезда на монорепозиторий; фактический
уровень — 0.65 % против 4.53 % изначально). История измерений, список извлечённых
кластеров и — что важнее — список дублирований, оставленных ОСОЗНАННО, в
[`monorepo.md`](monorepo.md).

## Проверки целостности

Три проверки, каждая закрывает конкретный способ тихо всё сломать:

```bash
uv lock --check                                 # устаревший лок удаляет рёбра графа
uv run python tools/check_docker_manifests.py    # список COPY в Dockerfile vs члены workspace
npx nx graph --file=/tmp/g.json && uv run python tools/check_graph_edges.py /tmp/g.json
```

CI (`.github/workflows/ci.yml`) прогоняет их ДО `nx affected` — иначе изменение
библиотеки может уехать непротестированным.

## Непрерывная интеграция

`.github/workflows/ci.yml`, шесть job — **только на pull request в `main`**:

| Job | Что делает |
|---|---|
| `checks` | гейты целостности, затем `nx affected` — `lint` (ruff), `typecheck` (mypy) и `test`. **Матричная по версии Python** |
| `affected-suites` | считает список функциональных наборов для матрицы ниже |
| `lint-report` | HTML-отчёт по ruff + wemake + mypy, артефактом прогона |
| `duplication` | `jscpd` против порога в `.jscpd.json` |
| `functional` | по одной ветви матрицы на затронутый набор, каждая — на своём демоне Docker |
| `notify` | итог прогона в Telegram |

**Триггер — один: `pull_request` с `branches: [main]`.** Прямого прогона на
`push` нет намеренно: ветка `main` защищена (см. ниже), коммит попадает туда
единственным путём — через PR, который этот же workflow уже прогнал, и второй
прогон на push проверял бы то же дерево файлов второй раз, тратя минуты раннера
и присылая второе уведомление в Telegram за один и тот же код. `branches` здесь
фильтрует **целевую** ветку PR, а не исходную.

### Защита ветки `main`

*Settings → Branches → Branch protection rules*, правило на `main` (то же
одной командой: `gh api -X PUT repos/:owner/:repo/branches/main/protection …`):

| Настройка | Значение | Зачем |
|---|---|---|
| Require a pull request before merging | вкл., **0** одобрений | без этого «защищённая» ветка всё равно принимает прямой push; нулевое число одобрений — потому что ревьюер в репозитории один и он же автор |
| Do not allow bypassing the above settings | вкл. | иначе правило не распространяется на администратора, то есть на единственного, кто и может пушить в `main` |
| Allow force pushes / deletions | выкл. | переписанная история `main` ломает `nx affected`: базу сравнения он берёт из истории |

Прямой `git push origin main` после этого отвечает
`protected branch hook declined` — работа идёт через ветку и PR.

### HTML-отчёт по линтерам

Собирает [`tools/lint_report.py`](../tools/lint_report.py) — один
самодостаточный файл (без внешних стилей и скриптов, со светлой и тёмной темой),
в котором сведены три линтера: карточки со счётчиками, топ кодов и раскрывающиеся
секции по файлам, худшие сверху.

```bash
uv run python tools/lint_report.py                # -> .lint-report/index.html
uv run python tools/lint_report.py --only wemake  # один линтер
```

Разбор трёх машинных форматов (`ruff --output-format=json`, плейсхолдеры
`flake8`, `mypy --output=json`) и экранирование чужого вывода живут в коде и
покрыты тестами (`npx nx run tools:test`) — по той же причине, что и
`notify_telegram.py`: в `run:`-блоке YAML это не запускается локально и не
проверяется ничем.

Граница «провал / не провал» здесь смещена намеренно: **найденные замечания —
не провал** (шаг вышел бы красным за то же, за что уже отвечает `checks`, а
советник красил бы прогон всегда). Ненулевой код возвращается, только если
линтер не смог отработать — упал, не найден, отдал неразбираемый вывод. Это не
формальность: упавший `flake8` выглядит в отчёте ровно как чистый код, и
единственный признак разницы — строка вывода, которая не разобралась.

Отчёт выгружается артефактом `lint-report` каждого прогона, а счётчики дублируются
в *Summary* прогона — чтобы увидеть цифры, не скачивая архив.

**Матрица версий Python — `3.13` и `3.14`: нижняя и верхняя границы
поддерживаемого диапазона.** 3.13 — это планка `requires-python` всех 11 пакетов
workspace, и ветвь стережёт её от синтаксиса новее заявленного минимума; 3.14 —
текущая стабильная версия, и её ветвь ловит поломки от свежего интерпретатора и
его колёс заранее, а не в день переезда. Ветви независимы (`fail-fast: false`),
версия входит в ключ кеша Nx: входы задач у ветвей совпадают побайтово, и без
этого вторая версия получала бы зелёный результат, посчитанный на первой.

Ниже 3.13 матрица не расширяется: uv workspace делит одно разрешение
зависимостей и одну планку (понизить её можно только всем сразу), а код
использует generics из PEP 695 (`class BaseService[ModelType]`), что на 3.10 и
3.11 — синтаксическая ошибка, то есть прогон падал бы на импорте. Полный список
того, что для этого нужно сделать, — комментарием над матрицей в самом workflow.

Отдельная тонкость, без которой матрица была бы декоративной: у целей `test`
трёх библиотек стоял ключ `uv run --python 3.13`, а он старше по приоритету, чем
`UV_PYTHON` из ветви матрицы. Все три набора гонялись на 3.13 в обеих ветвях —
вторая молча проверяла ровно то же, что и первая. Ключ снят; версию теперь
задаёт `UV_PYTHON` в CI и `.python-version` локально.

### Уведомление в Telegram

Шлёт [`tools/notify_telegram.py`](../tools/notify_telegram.py)
— обычный async-скрипт на `aiohttp` (тот же HTTP-клиент, что и во всех сервисах),
а не `run: curl …` и не сторонний action (тот пришлось бы пришпиливать по SHA и
обновлять — при том, что он получает токен бота). Логики там ровно две вещи, и обе в YAML не проверяются
ничем: какой прогон считается успешным (`skipped` — норма) и экранирование
заголовка коммита, который пишет автор PR. Поэтому она вынесена в код, покрыта
тестами (`npx nx run tools:test`) и запускается локально:

```bash
CI_NEEDS='{"checks":{"result":"success"}}' \
    uv run python tools/notify_telegram.py --dry-run   # напечатать, не отправляя
```

В CI шаг запускается как `uv run --no-project --with aiohttp` — синхронизировать
109 зависимостей workspace ради одного HTTP-запроса дороже, чем поставить один
пакет.

Сообщение приходит на любой итог, кроме отменённого прогона. Нужны два секрета
репозитория (*Settings → Secrets and variables → Actions*):

| Секрет | Значение |
|---|---|
| `TELEGRAM_BOT_TOKEN` | токен бота от [@BotFather](https://t.me/BotFather) |
| `TELEGRAM_CHAT_ID` | id чата или канала (для канала — с минусом: `-100…`) |

Без них скрипт пишет `::notice::` и выходит с нулём — в PR из форка секреты
недоступны по построению, и падать на этом CI не должен. А вот отказ самой
отправки — это выход с единицей: молчащее уведомление хуже отсутствующего.
Повторы делаются только на сбоях, которые могут пройти сами (сеть, 5xx, 429);
401 и 400 — это неверный токен или чат, и три попытки по нарастающей паузе лишь
задержали бы шаг.

Как это выглядит в чате — [скриншот в корневом README](../README.md#непрерывная-интеграция).
