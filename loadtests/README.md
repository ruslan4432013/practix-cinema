# Нагрузочные сценарии (k6)

Единый профиль нагрузки на все публичные ручки. До этого измерения были только
у Movies API (`wrk`, таблица в корневом README), а заявленная пропускная
способность коллектора (≥1000 событий/с) оставалась проектной оценкой:
измерена была лишь латентность публикации в буфер продюсера.

`wrk` заменён на k6 не из моды: `wrk` умеет долбить один URL, а здесь нужна
**смесь** запросов с телом, с токеном и без, одиночных и пачками — то есть
сценарий, а не поток одинаковых GET'ов.

## Запуск

Стек должен быть поднят (`docker compose up -d`), точка входа — Nginx на `:80`.

```bash
# Ingest-ручка коллектора: смесь одиночных событий и пачек
docker run --rm --network host -v "$PWD/loadtests:/scripts" \
    grafana/k6:0.55.0 run /scripts/ingest.js

# Movies API: чтение каталога и поиск
docker run --rm --network host -v "$PWD/loadtests:/scripts" \
    grafana/k6:0.55.0 run /scripts/movies.js

# Auth: логин и обновление токенов
docker run --rm --network host -v "$PWD/loadtests:/scripts" \
    grafana/k6:0.55.0 run /scripts/auth.js

# Рекомендации: проектные 100 RPS. Пороги — SLO из раздела 5.1 diploma-tz.md.
# FILM_IDS обязателен: без него сценарий не стартует и говорит, почему — идти за
# похожими к несуществующему фильму значит собирать 404, а не измерять сервис.
FILMS=$(docker compose --env-file .env -f infra/compose/docker-compose.yml \
    --project-directory infra/compose exec -T recs-db psql -U postgres -d recs_database \
    -t -A -c "SELECT string_agg(film_id::text, ',') FROM (SELECT DISTINCT film_id FROM similar_item LIMIT 200) s")
docker run --rm --network compose_movies_net -v "$PWD/loadtests:/scripts" \
    -e BASE_URL=http://nginx -e FILM_IDS="$FILMS" grafana/k6:0.55.0 run /scripts/recommendations.js

# И отдельно — что лимитер при этом жив: перебор с ОДНОГО адреса упирается в зону
docker run --rm --network compose_movies_net -v "$PWD/loadtests:/scripts" \
    -e BASE_URL=http://nginx grafana/k6:0.55.0 run /scripts/recs-limiter.js
```

Сценарии рекомендаций запускаются **в сети compose** (`--network
compose_movies_net`, точка входа — `http://nginx`), а не через опубликованный
порт. Причины две: `--network host` не работает на macOS и Windows так, как в
Linux, а адрес контейнера в сети compose попадает в диапазон, который nginx
считает доверенным прокси — без этого подстановка адреса клиента (см. ниже) не
сработала бы. Имя сети — это имя проекта compose плюс `movies_net`; проверить
можно `docker network ls`.

Остальным сценариям сеть compose не нужна; на macOS и Windows им достаточно
задать адрес явно:

```bash
docker run --rm -v "$PWD/loadtests:/scripts" -e BASE_URL=http://host.docker.internal \
    grafana/k6:0.55.0 run /scripts/ingest.js
```

## Как рекомендации доходят до проектных 100 RPS

Раздел 4 ТЗ считает пик ~83 RPS и проектирует на 100. Прямо снять эту цифру
одним генератором нельзя: `limit_req_zone ... zone=recs_read rate=50r/s`
(`infra/nginx/nginx.conf:197`) считает **по адресу**, а генератор приходит с
одного — выше 50 r/s начались бы честные 429, и замер превратился бы в замер
лимитера.

Поэтому `recommendations.js` раскладывает итерации по `CLIENTS` синтетическим
адресам через `X-Forwarded-For`. Это работает потому, что nginx уже настроен
доверять прокси из приватных сетей (`set_real_ip_from`, `real_ip_recursive on`,
`nginx.conf:226-234`), а контейнер k6 в сети compose в такую сеть попадает:
модуль `realip` подставляет адрес в `$binary_remote_addr` раньше фазы, на
которой работает `limit_req`. При `RPS=100` и `CLIENTS=8` на адрес приходится
12,5 r/s против зоны в 50 — четырёхкратный запас.

**Адреса берутся из `203.0.113.0/24` (TEST-NET-3), и это не косметика.** Адрес
из доверенной сети (`10/8`, `172.16/12`, `192.168/16`, `127/8`) при
`real_ip_recursive on` был бы пропущен как «ещё один прокси», nginx откатился бы
к адресу контейнера, и все синтетические клиенты молча схлопнулись бы в один —
то же ограничение, только незаметное.

Конфигурация стенда при замере **не меняется**: лимитер остаётся включённым.
Что доказывает каждый из двух прогонов:

| Прогон | Доказывает |
|--------|------------|
| `recommendations.js` (100 RPS, 8 адресов) | выдача держит проектную нагрузку через nginx, в SLO раздела 5.1, и лимитер ей не мешает — 429 ноль, и это порог `recs_rate_limited` |
| `recs-limiter.js` (200 RPS, 1 адрес) | зона `recs_read` по-прежнему режет перебор, и режет 429-м, а не 5xx |

Порознь ни один из них не полон: первый без второго не отличает «лимитер не
мешает» от «лимитера нет», второй без первого ничего не говорит о выдаче. Вместе
они доказывают и саму подстановку адреса — если бы nginx её игнорировал, ноль
429 в первом прогоне был бы невозможен.

Прямо посмотреть, каким адрес доехал до лимитера, можно в журнале nginx: поле
`remote_addr` там пишется уже после `realip`, поэтому у прогона оно должно быть
`203.0.113.x`, а не адресом контейнера.

```bash
docker compose --env-file .env -f infra/compose/docker-compose.yml \
    --project-directory infra/compose logs nginx --tail 9000 \
    | grep -o '"remote_addr":"[^"]*"' | sort | uniq -c | sort -rn | head
```

Ожидание — `CLIENTS` строк примерно равного веса: раскладка идёт по номеру
итерации, а не случайно, поэтому перекос означает поломку, а не статистику.

Замер — **тёплый, установившийся режим**: отдельный сценарий `warmup` обходит
весь список `FILM_IDS` по разу до начала плато, и пороги привязаны к плато
(`{scenario:read}`). Первое обращение к фильму идёт мимо пустого Redis в
PostgreSQL и стоит ~550 мс (`docs/recommendations.md`) — без прогрева p99
пробивала бы механика замера, а не сервис. Холодная цена документирована
отдельно и в SLO не входит.

Счётчики `recs_source_similar` / `_personal` / `_popular` в сводке говорят, что
именно отдавалось: 200 не значит «выдача», деградация тоже отвечает 200 (это её
смысл). Прогон, в котором похожие целиком подменились популярным, без этих чисел
выглядит идеально здоровым.

С `ACCESS_TOKEN` «главная» в смеси идёт в `/api/v1/recommendations/me` вместо
`/popular`. У свежезарегистрированного пользователя персональной полки нет —
синтетические зрители генератора не являются пользователями Auth, — поэтому
ответ будет `source=popular`. Это честный путь «новый зритель», и счётчики
назовут его прямо; выдавать такой прогон за замер персональной выдачи нельзя.

## Переменные окружения

| Переменная | По умолчанию | Смысл |
|------------|--------------|-------|
| `BASE_URL` | `http://localhost` | Точка входа (Nginx) |
| `RPS` | `100` | Интенсивность `recommendations.js` в **запросах** в секунду — в той же единице, в которой считает раздел 4 ТЗ. Итерации выводятся делением на 4 (столько запросов в итерации) |
| `CLIENTS` | `8` | Со скольких синтетических адресов идёт нагрузка (`recommendations.js`). Держать `RPS / CLIENTS` заметно ниже 50 r/s зоны `recs_read`; иначе прогон валит порог `recs_rate_limited` |
| `WARMUP` | `30s` | Окно прогрева перед измеряемым плато (`recommendations.js`): обход всего `FILM_IDS` по разу, в пороги не входит |
| `LIMITER_RPS` | `200` | Интенсивность `recs-limiter.js` с одного адреса — заведомо выше зоны |
| `FILM_IDS` | **обязателен** | Список идентификаторов фильмов через запятую (`recommendations.js`). Без него сценарий останавливается в init-контексте с кодом 108 и рецептом в сообщении: синтетический идентификатор — не фильм каталога, выдача отвечает на него 404, и прогон валит `http_req_failed`, ничего не измерив. `DISTINCT` в запросе стоит **до** `LIMIT` не случайно: у каждого фильма в `similar_item` десятки соседей, и `LIMIT 200` по строкам даёт около десятка фильмов |
| `VUS` | зависит от сценария | Число виртуальных пользователей на плато |
| `DURATION` | `1m` | Длительность плато |
| `ACCESS_TOKEN` | пусто | Если задан, часть трафика идёт авторизованной |

## Пороги (thresholds)

Пороги — не украшение: k6 выходит с ненулевым кодом при их нарушении, поэтому
сценарий годится как шаг CI на релизных ветках.

Для ingest порог по ошибкам жёсткий — **ноль 5xx**. Это прямая проверка
основного инварианта сервиса: приём события не возвращает 5xx никогда, даже
когда Kafka недоступна (событие уходит в буфер деградации). 429 при этом
ошибкой не считается — это штатный ответ rate limit.

## Результаты замера

Рекомендации, прогон на значениях по умолчанию (100 RPS с восьми адресов, плато
60 с после 30 с прогрева, 200 фильмов из дампа, витрина на 49 719 синтетических
зрителях). Плато — 6 000 запросов, то есть проектные 100 RPS раздела 4 ТЗ
достигнуты, а не заявлены:

| SLI | SLO | замер | |
|---|---|---:|---|
| p95 | < 200 мс | 43,9 мс | ✅ |
| p99 | < 300 мс | 47,8 мс | ✅ |
| 5xx | < 0,1 % | 0 из 6 000 | ✅ |
| 429 | 0 | 0 | ✅ |

Парный прогон `recs-limiter.js` (200 RPS с одного адреса): 1 401 отказ из
2 001 запроса, обслужено 600 — `50 r/s × 10 с + burst 100`. Ноль 429 в первом
прогоне и семьдесят процентов во втором доказывают подстановку адреса и живой
лимитер **только вместе**; порознь каждое число объясняется и поломкой.

Длительность батча обучения — 19,5 с на 494 661 взаимодействии (36,1 с вместе с
записью витрины) при SLO «< 2 ч». Методика, полные числа и оговорки —
[`docs/recommendations.md`](../docs/recommendations.md#замеры-slo).

Замеров по ingest, Movies API и Auth этими сценариями пока нет: заявленная
пропускная способность коллектора (≥1000 событий/с) остаётся проектной оценкой.

## Что стоит проверить отдельно

Деградация под нагрузкой: остановить `kafka-0/1/2` в середине плато и убедиться,
что доля 5xx осталась нулевой, а `ugc_fallback_buffer_size` в Prometheus растёт.
Сейчас деградация проверена только на спокойном трафике
(`tests/functional/ugc/test_degradation.py`).
