# Секционирование `login_history`

Документ отвечает на вопрос спринта: какую таблицу секционировать, по какому
критерию и почему — с прицелом на будущее, когда записей станут миллионы.

## Что секционируем и почему именно это

Секционируется **`login_history`** (история входов), а не `users`.

- `login_history` — append-only лог: строка пишется на каждый вход. При 1 млн
  пользователей, нескольких клиентах (web, мобильное приложение, SmartTV) и
  регулярных перелогинах таблица растёт неограниченно — 2 → 5 → 10 млн строк.
  Именно такие таблицы деградируют первыми и выигрывают от секционирования.
- `users` растёт линейно и ограничен числом реальных людей, часто читается по
  первичному ключу и участвует во внешних ключах. Секционирование дало бы мало
  выгоды и усложнило бы уникальность логина/email и FK. Поэтому `users` не трогаем.

## Выбранная схема: composite RANGE(auth_date) → LIST(device_type)

```
login_history                         PARTITION BY RANGE(auth_date)
 ├ login_history_2025                  PARTITION BY LIST(device_type)
 │   ├ login_history_2025_web / _mobile / _smart / _other (DEFAULT)
 ├ login_history_2026  (те же 4 секции)
 └ login_history_2027  (те же 4 секции)
```

**Верхний уровень — RANGE по `auth_date` (по годам).** Это главный аргумент
масштабирования: данные растут во времени, большинство запросов смотрят на
недавнее окно, а устаревшие данные удаляются целой секцией через
`DROP TABLE`/`DETACH PARTITION` вместо построчного `DELETE`. Работает partition
pruning по дате.

**Второй уровень — LIST по `device_type` (web / mobile / smart).** Тип устройства
определяется из User-Agent при входе (`services/user_agent.py`). Разрез по
устройству полезен для безопасности и аналитики («покажи входы со SmartTV»,
«необычное устройство → доп. проверка»), даёт pruning по устройству и позволяет
держать разный набор индексов и политику хранения на секцию. Секция `*_other`
(DEFAULT) страхует от значений вне web/mobile/smart.

### Следствия для схемы

- PostgreSQL требует, чтобы уникальный/первичный ключ секционированной таблицы
  включал столбцы ключа секционирования **каждого** уровня. Поэтому первичный
  ключ составной — **`(id, auth_date, device_type)`**, а `device_type` объявлен
  `NOT NULL`.
- Индексы не наследуются от «обычной» таблицы автоматически, но индекс,
  объявленный на родительской секционированной таблице, распространяется на все
  секции. Для запроса истории конкретного пользователя заведён
  `ix_login_history_user_date (user_id, auth_date DESC)`.

## Почему не по региону и не по возрасту

Задача упоминает регионы и возрастные ограничения — это атрибуты **пользователя**,
а не события входа:

- **Регион.** Логичнее как ключ секционирования/шардирования на стороне `users`
  (LIST по коду страны/региона). В `login_history` региона нет; тащить его туда —
  денормализация ради ключа. Если понадобится географический разрез логов, дешевле
  добавить индекс, чем менять ключ секционирования.
- **Возрастные ограничения.** Тоже свойство пользователя; для фильтрации
  достаточно индекса на `users`. Как ключ секционирования возраст даёт мало
  логически однородных групп и не помогает удалять старые логи.

Оба критерия рассмотрены и осознанно отклонены в пользу пары «время + устройство»,
которая напрямую решает проблему роста лог-таблицы.

## Сопровождение

Сейчас секции на будущие годы создаются заранее (2025, текущий и следующий год):
в миграции — статически, в приложении — листенером `after_create` в
`models/entity.py` (используется тестами через `Base.metadata.create_all`). Для
продакшена автоматическое заведение новых годовых секций стоит переложить на
расширение **pg_partman**, чтобы вставка не упала при переходе в год без секции.
