# recsys-trainer — офлайн-обучение рекомендаций

Батч по расписанию: читает просмотры, обучает модели, раскладывает витрину.
Онлайн-часть — [`recommendations-api`](../recommendations-api/README.md), она
только читает готовое. Требования и журнал решений —
[`docs/diploma-tz.md`](../../docs/diploma-tz.md), разбор устройства —
[`docs/recommendations.md`](../../docs/recommendations.md).

Считать рекомендации в момент запроса нельзя (ADR-001): коллаборативная
фильтрация — это перемножение матриц на сотнях тысяч строк, а бюджет ответа —
300 мс. Поэтому система разрезана на батч, который думает, и выдачу, которая
только читает.

## Команды

```bash
DC="docker compose --env-file .env -f infra/compose/docker-compose.yml --project-directory infra/compose"

# T2.1 — сколько данных есть НА САМОМ ДЕЛЕ. Первая команда на новом стенде.
$DC exec recsys-trainer python -m practix_recsys_trainer.cli stats

# T2.3 — синтетическая история просмотров
$DC exec recsys-trainer python -m practix_recsys_trainer.cli generate \
    --sink clickhouse --users 5000 --seed 42     # массово, напрямую в ugc.film_views
$DC exec recsys-trainer python -m practix_recsys_trainer.cli generate \
    --sink api --users 40 --seed 7               # через боевой путь коллектор→Kafka→ETL

# T2.2 / T2.4 — выгрузка матрицы и сплит по времени
$DC exec recsys-trainer python -m practix_recsys_trainer.cli dataset

# E3 / E6 — полный прогон и раскладка витрины
$DC exec recsys-trainer python -m practix_recsys_trainer.cli train

# E5 — качество против baseline «просто популярное»
$DC exec recsys-trainer python -m practix_recsys_trainer.cli evaluate --k 10
```

## Источники сигнала

| Сигнал | Откуда | Роль |
|---|---|---|
| `video_progress`, `video_completed` | ClickHouse, `ugc.film_views` | **основной**, неявный |
| Оценки 0..10 | `ugc-db`, таблица `likes` | дополнительный вес |
| Список фильмов | `theatre-db`, `content.film_work` | снимок каталога и покрытие |

ADR-005: учим на просмотрах, а не на оценках. Оценок на порядки меньше и они
смещены — их ставят те, у кого сильные эмоции. Оценка не создаёт
взаимодействия, а лишь усиливает или ослабляет уже существующее.

Считается `uniq(view_id)`, а не `count()`: метки прогресса идут десятками на
один просмотр, и `count()` измерял бы длину фильма, а не его популярность.

Чужие базы читаются напрямую — тем же офлайновым доступом, каким
`etl-elasticsearch` читает `theatre-db` django-админки. Соединения read-only,
на горячем пути их нет, новых ключей конфигурации не заводится: `CH_*`,
`POSTGRES_*`, `UGC_API_POSTGRES_*` уже описывают эти хранилища.

## Модели

* **Со-встречаемость** (E3) — косинус между столбцами матрицы. Нормировка
  обязательна: без неё «похожим на всё» оказался бы самый популярный фильм,
  потому что он пересекается со всеми. Граница применимости зафиксирована в
  разделе 6 ТЗ — матрица квадратична по каталогу, до ~10 000 фильмов.
* **ALS** (E6, ADR-007) — `implicit`, матричная факторизация на той же матрице.
  Взята библиотека, а не сервис: за швом витрины её не видно, и заменить её
  можно, не тронув ни API, ни nginx.
* **Популярное** — топ за окно. Считается **всегда**, даже когда обе модели не
  дали ни строки: витрина без популярного оставила бы выдачу без последней
  ступени лестницы деградации.

**Просмотренное исключается здесь, а не библиотекой.** У `implicit` есть флаг
`filter_already_liked_items`, но он не держит слова: когда неотфильтрованных
кандидатов меньше запрошенного `N`, библиотека добивает выдачу теми самыми
просмотренными позициями. На матрице 24×12 запрос десяти рекомендаций возвращал
шесть новых и четыре просмотренных — то есть бил ровно по активным зрителям.
F4.3 не знает слова «обычно», поэтому строка пользователя перепроверяется явно.

## Генератор синтетики: зачем и почему с кластерами

Стенд поднимается с пустым ClickHouse. Раздел 8 ТЗ числит «данных мало для
обучения» риском номер один и прямо закладывает генератор в DoD эпика E2.

Фильмы берутся **настоящие**, из каталога: выдуманные UUID дали бы рекомендации
на фильмы, которых нет, и сквозной путь стал бы проверкой самого себя.

Зрители разбиты на **вкусовые кластеры**, и это условие осмысленности всей
проверки. При равномерно случайных просмотрах у любых двух фильмов будет
примерно одинаковое пересечение аудитории, со-встречаемость выродится в шум, и
E5 покажет, что модель не лучше baseline — правдой о генераторе, а не о модели.
Юнит-тест проверяет ровно это свойство: на сгенерированных данных модель обязана
обгонять популярное.

Два слива отвечают на разные вопросы. `clickhouse` даёт объём, из которого
учится модель. `api` проверяет живучесть стыка — и уже поймал реальное
расхождение: генератор слал качество `4k`, которого нет в словаре коллектора.

## Идемпотентность и один писатель

Три требования закрываются одной конструкцией (`shelf/writer.py`):

* **F0.1** — батч всегда пишет **новую** версию; версия входит в первичный ключ
  каждой таблицы списков, поэтому повторный прогон физически не может удвоить
  строки. Второй тик планировщика отсекается раньше: `run_key` уникален и
  привязан к часу запуска, а не к UUID.
* **F0.2** — указатель переставляется одной транзакцией и только на версию со
  статусом `ready`.
* **Ровно один писатель** (раздел 5.3) — `pg_advisory_lock`. Масштабировать
  репликами нельзя: два писателя означают две версии из пересекающихся данных.

Прогрев Redis идёт **после коммита** и выставляет указатель **последним**:
иначе выдача пошла бы за ключами, которых ещё нет, и переключение версии само
себе создавало бы пик промахов.

## Почему это долгоживущий процесс, а не cron

F0.4 требует, чтобы возраст витрины был виден: устаревшая модель — инцидент, а
не тишина. Одноразовый процесс экспортирует метрики только пока работает, то
есть Prometheus не застаёт его почти никогда, и «обучение не запускалось третьи
сутки» выглядит точно так же, как «всё хорошо».

Гейджи витрины заполняются из **самой витрины**, а не из результата последнего
прогона этого процесса: на стенде обучение часто запускают отдельной командой,
и метрика покрытия иначе показывала бы ноль при полной витрине, а алерт
`RecsCatalogCoverageLow` срабатывал бы на пустом месте.

## Профиль `warehouse`, а не свой

Батчу нужен ClickHouse, который живёт там же. Отдельный профиль был бы третьим,
который надо не забыть повторить на `down -v`, а привязка к профилю источника
читается однозначно: нет ClickHouse — нечему и учиться. Выдача при этом в ядре
и работает без профиля: витрина пуста, отдаётся популярное, страница фильма цела.

## Системная зависимость образа

Единственный таргет в репозитории, которому нужен `libgomp1`: `implicit` собран
с OpenMP. Отказ без неё очень тихий — колесо ставится, образ собирается, падает
только вызов ALS в рантайме, внутри `except`, который честно публикует витрину
без персональной выдачи. То есть E6 молча не работал бы, а всё остальное
выглядело бы исправным.

## Не сделано (осознанно)

- **Усечение до top-K соседей при записи со-встречаемости.** Матрица
  квадратична по каталогу: на сегодняшних ~1 000 фильмов она целиком помещается
  в память и считается за минуты, на 100 000 наименований это 10¹⁰ пар, и она
  не посчитается никогда. Отсюда зафиксированная в разделе 6 ТЗ **известная
  граница применимости — до ~10 000 фильмов**. Лечится усечением на этапе
  записи, и это работа, которой в плане нет: она меняет форму данных в витрине,
  а не параметр.
- **Дообучение в реальном времени.** Суточная свежесть — принятое решение
  (SLO раздела 5.1 ТЗ). Реакция «в тот же день» достигается ручным запуском
  `train`, а не архитектурой: онлайн-обновление требует онлайн-слоя, которого
  здесь нет по ADR-001.
- **Отдельный feature store.** Признак здесь ровно один — сама матрица
  взаимодействий, и она строится за один прогон из ClickHouse командой
  `dataset`. Отдельное хранилище признаков окупается, когда моделей и
  потребителей много; здесь оно добавило бы ещё одно состояние, которое можно
  рассинхронизировать с источником.
- **Горизонтальное масштабирование — и его не должно быть.** Раздел 5.3 ТЗ:
  витрину пишет **ровно один** писатель, иначе F0.1 перестаёт быть достижимой —
  две реплики дадут две версии из пересекающихся данных. `pg_advisory_lock` —
  страховка от второго запуска, а не разрешение на реплики. Растём вертикально;
  при исчерпании батч режется по типам моделей на отдельные джобы, каждая из
  которых по-прежнему единственный писатель своей части.
- **Подбор гиперпараметров.** Дефолты ALS (`core/config.py`: факторы,
  итерации, регуляризация, `alpha`) зафиксированы намеренно и не подбирались:
  это окрестности общепринятых значений, а `alpha` — множитель уверенности из
  статьи Hu-Koren-Volinsky. Перебор требует отдельного прогона со своим сплитом
  на каждую комбинацию, то есть собственного стенда и бюджета времени;
  при этом E5 и без него показывает превосходство над baseline «просто
  популярное» примерно на порядок по precision@10.
