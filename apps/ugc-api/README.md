# UGC API — оценки, закладки, рецензии

Синхронный сервис пользовательского контента. Реализует выводы исследования
[`research/ugc-storage/`](../../research/ugc-storage/README.md): PostgreSQL,
схема с преагрегатом рейтинга, отдельный сервис вместо расширения коллектора.

**Хранилище здесь PostgreSQL, а не MongoDB, и это результат замера, а не
умолчание.** Исследование сравнило три кандидата на одинаковом датасете класса S
(10 млн лайков); MongoDB — на настоящем шардированном кластере — проиграла по
p99 во всех одиннадцати сценариях, на рецензиях с сортировкой по полезности —
в 169 раз (152.3 против 0.9 мс). Схема ниже дословно повторяет измеренную, имена
индексов включительно, — иначе цифры исследования перестали бы относиться к
этому коду. Путь на MongoDB при этом описан и проверен: ключи шардирования
выбраны, ошибка с покрывающим индексом в шардированной коллекции найдена и
разобрана, так что переезд будет миграцией данных, а не перепроектированием.

## Почему это отдельный сервис

`analytics-collector` построен на инварианте «ingest никогда не отдаёт 5xx»:
Kafka недоступна — событие уходит в Redis-буфер, Redis тоже — событие
отбрасывается с метрикой. Это допустимо потому, что аналитическое событие можно
потерять. Оценку потерять нельзя: ответ «принято» обязан означать «сохранено».
Семантика прямо противоположная, и в одном процессе она либо ослабила бы
инвариант коллектора, либо дала бы новым ручкам чужой контракт.

Своя база `ugc-db`, а не таблицы в `theatre-db`: профиль нагрузки UGC (чтений на
порядок больше записей, запись конкурирует за преагрегат) не должен влиять на
каталог и на вход в систему.

## Данные

Пять таблиц, дословно из исследования — имена индексов включительно.

| Таблица | Ключи и индексы | Зачем так |
|---|---|---|
| `likes` | PK `(user_id, film_id)`; `(film_id, rating)`, `(user_id, rating, updated_at)` | Два паттерна доступа — «по фильму» и «по пользователю» — одним индексом не закрыть |
| `film_rating` | PK `film_id`; `ratings_count`, `ratings_sum`, **гистограмма из 11 чисел** | Преагрегат; см. ниже |
| `bookmarks` | PK `(user_id, film_id)`; `(user_id, created_at)` | Сортировок не требуется |
| `reviews` | PK `review_id`; по индексу на каждый порядок сортировки | Новый алгоритм ранжирования стоит одного индекса |
| `review_votes` | PK `(review_id, user_id)` | Идемпотентность голосования; счётчики денормализованы в `reviews` |

**Гистограмма, а не пара счётчиков «лайки/дизлайки».** Порог, с которого оценка
считается лайком, — продуктовое решение (`UGC_API_LIKE_THRESHOLD`), и оно будет
меняться. Из 11 чисел любой порог считается за O(1); пара счётчиков потребовала
бы пересчёта по всей таблице при каждом изменении правила. Порог возвращается в
ответе, чтобы клиент не мог разойтись с сервером в том, что считается лайком.

**Отступления от измеренной схемы — два, оба помечены в миграции:** уникальность
`(film_id, user_id)` в `reviews` (продуктовое правило «одна рецензия на фильм»,
без индекса его не выразить) и `NULLS LAST` в индексе по `author_rating` (поле
необязательное, а PostgreSQL при `DESC` ставит NULL первыми).

## Запись: одна транзакция и блокировка

В стенде оценка и преагрегат писались двумя независимыми транзакциями на
autocommit — для замера задержки это неважно, для сервиса недопустимо. Здесь всё
идёт **одной** транзакцией, а перед ней берётся `pg_advisory_xact_lock` по паре
(пользователь, фильм).

Блокировка закрывает два состязания, которых стенд не доставал, потому что
никогда не писал одну пару параллельно:

* **строка уже есть** — подзапрос «прошлая оценка» читает снимок начала
  оператора, а `ON CONFLICT DO UPDATE` меняет уже новую версию строки: вторая
  транзакция посчитала бы дельту от устаревшего значения;
* **строки ещё нет** — обе транзакции видят «оценки нет» и обе прибавляют `+1`
  к счётчику. Блокировкой строки это не лечится: блокировать нечего.

Блокировать строку `film_rating` было бы проще, но это выстроило бы в очередь
всех оценивающих популярный фильм. Разным пользователям одного фильма
блокировка не нужна: преагрегат меняется не «прочитал — посчитал — записал», а
`+= дельта` внутри одного оператора.

Арифметика дельт вынесена в `services/aggregate.py` и покрыта юнит-тестами —
исследование прямо указывает на неё как на место, где легко ошибиться.

## Ручки

Swagger — `/api/ugc/openapi` (`/api/openapi` занят Movies API,
`/api/analytics/openapi` — коллектором).

| Метод и путь | Токен | Что делает |
|---|---|---|
| `PUT /api/v1/likes/{film_id}` | да | Поставить или изменить оценку 0..10 |
| `DELETE /api/v1/likes/{film_id}` | да | Снять оценку |
| `GET /api/v1/likes/me` | да | Понравившиеся фильмы (сценарий R1) |
| `GET /api/v1/ratings/{film_id}` | нет | Рейтинг фильма из преагрегата (R3c) |
| `PUT/DELETE /api/v1/bookmarks/{film_id}` | да | Закладка, идемпотентно |
| `GET /api/v1/bookmarks` | да | Закладки пользователя (R4) |
| `POST /api/v1/reviews` | да | Написать рецензию; 409 на вторую для того же фильма |
| `GET /api/v1/reviews?film_id=…&sort=new\|useful\|rating` | нет | Рецензии фильма (R5) |
| `GET /api/v1/reviews/{review_id}` | нет | Рецензия целиком, с телом |
| `DELETE /api/v1/reviews/{review_id}` | да | Своя — всегда, чужая — с ролью `admin` |
| `PUT/DELETE /api/v1/reviews/{review_id}/vote` | да | Голос за полезность и его отзыв |
| `GET /health/live` · `/health/ready` | нет | Пробы; наружу Nginx отдаёт 404 |

**Агрегации «на лету» (сценарии R2/R3) наружу нет намеренно**: она в 13 раз
медленнее преагрегата и является единственным местом, где 200 мс реально могли
не выдержать. Выставлять медленный путь по умолчанию — значит гарантировать, что
кто-нибудь вызовет его со страницы фильма.

`user_id` берётся **только** из подписи токена: своей таблицы пользователей у
сервиса нет, а тела запросов используют `extra='forbid'` и поля `user_id` не
имеют — присланный в теле идентификатор даёт 422, а не тихую подмену.

Подпись проверяется локально, общим с Auth секретом, без сетевых обращений:
падение Auth не мешает ставить оценки. Денилист отозванных токенов читается из
Redis Auth-сервиса с политикой `on_error='deny'` — в отличие от коллектора,
который выбирает `allow`, потому что потерянное событие дешевле отказа.

## Ограничение частоты

В приложении его нет, и это решение. В репозитории уже два разошедшихся
лимитера (фиксированное окно в Auth, скользящее в коллекторе), а `jscpd` —
жёсткий гейт; третья копия дала бы только дублирование. UGC-маршруты
ограничивает Nginx зоной `ugc_write` (20 r/s, burst 40) — там же, где уже
резолвится реальный адрес клиента, и без затрат воркера Python.

Лимит **по пользователю**, а не по адресу, потребовал бы читать субъект токена,
чего Nginx без njs не умеет. День, когда он понадобится, — это день, когда
лимитер стоит вынести в `practix_core`: три потребителя перестают быть
«библиотекой ради одного».

## Обслуживание преагрегата

```bash
docker compose ... exec ugc-api python -m practix_ugc_api.cli recount --check   # только сравнить
docker compose ... exec ugc-api python -m practix_ugc_api.cli recount           # пересчитать
```

`--check` печатает число разошедшихся фильмов и завершается ненулевым кодом,
поэтому годится и для cron, и для проверки в CI. Пересчёт идёт upsert'ом, а не
`TRUNCATE + INSERT`: `TRUNCATE` берёт `ACCESS EXCLUSIVE` и на время пересчёта
остановил бы чтение рейтингов всеми пользователями сразу.

## Не сделано (осознанно)

* **Метрика расхождения в Prometheus.** `/metrics` у сервиса нет — как и у Auth
  с Movies API. Расхождение находится командой `recount --check`; экспорт
  gauge'а потребовал бы либо однопроцессного режима, либо
  `PROMETHEUS_MULTIPROC_DIR`, и это отдельное решение.
* **Планировщик пересчёта.** В стеке нет cron; пересчёт — операторская команда.
* **Автопочинка расхождения.** Молчаливая перезапись агрегата спрятала бы
  ошибку, которая его породила.
* **`GET /reviews/me`.** У `reviews` нет индекса по `user_id`, и в измеренной
  схеме его тоже не было; ручка стоила бы seq scan либо ещё одного индекса.
* **Keyset-пагинация рецензий.** В исследовании мерился `LIMIT 20` без
  `OFFSET`, поэтому измеренные цифры верны для первой страницы.
* **401 на просроченный токен.** `async_fastapi_jwt_auth` отдаёт на него
  `JWTDecodeError` со статусом **422**, и статус берётся из библиотеки общим
  обработчиком `practix_core.jwt`. Клиенту это мешает: 422 не отличить от ошибки
  валидации тела, то есть непонятно, что надо обновить токен. Чинить это стоит
  один раз в `practix_core` — сразу для Auth, коллектора и этого сервиса, — а не
  переопределением в одном из трёх.
