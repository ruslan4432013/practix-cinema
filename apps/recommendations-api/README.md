# Recommendations API — выдача рекомендаций

Онлайн-часть рекомендательной системы: **читает готовое и не считает ничего**.
Модель обучает ночной батч [`recsys-trainer`](../recsys-trainer/README.md),
шов между ними — витрина в `recs-db`. Требования и журнал решений —
[`docs/diploma-tz.md`](../../docs/diploma-tz.md), разбор устройства —
[`docs/recommendations.md`](../../docs/recommendations.md).

## Ручки

| Метод | Что | Токен |
|---|---|---|
| `GET /api/v1/recommendations/similar/{film_id}` | «С этим смотрят»: соседи по со-просмотрам | не нужен |
| `GET /api/v1/recommendations/popular` | Топ за окно; он же путь деградации | не нужен |
| `GET /api/v1/recommendations/me` | Персональная выдача по `user_id` **из токена** | обязателен |
| `GET /health/live`, `/health/ready`, `/metrics` | Служебные | не нужен |

Общие параметры: `limit` (обрезается потолком `RECS_MAX_LIMIT`, а не отвергается
422 — вёрстка блока дело фронта) и `enrich=true` (дорисовать названия из Movies
API; по умолчанию выключено).

Документация — `/api/recommendations/openapi` (`/api/openapi` занят Movies API,
`/api/analytics` — коллектором, `/api/ugc` — UGC, `/api/shortener` — ссылками).

## Ответ всегда называет свой источник

```json
{"source": "similar", "version": 12, "items": [{"film_id": "...", "score": 0.25}]}
```

`source` — `similar` / `personal` / `popular`. Это требование F1.4, а не
украшение: деградация, о которой не сказано, — деградация, которую никто не
заметит. Код ответа при подмене персональной выдачи популярной остаётся 200, и
без этого поля авария была бы неотличима от здоровья.

`version` описывает, **откуда пришли отданные позиции**, а не то, что показывал
указатель. Позиций нет — значит и версии у них нет, поле `null`.

## Лестница деградации

Раздел 5.2 ТЗ: ни один отказ не имеет права превратиться в 5xx на странице
фильма. Вся лестница живёт в одном модуле — `services/degradation.py`:

1. горячий слой Redis жив — отдаём из него;
2. Redis лёг — читаем витрину из PostgreSQL (медленнее, но это ответ);
3. PostgreSQL лёг — отдаём последнее известное популярное из памяти процесса;
4. витрины нет / соседей нет / у пользователя нет истории — популярное, **200**;
5. и популярного ещё нет — 200 с пустым списком.

Единственный 404 — неизвестный `film_id`, и **только когда отсутствие
доказано**: непустой снимок каталога, в котором фильма нет. Недоступная база и
устаревший указатель — это «не знаю», а не «нет».

**У всего обработчика есть срок** (`RECS_REQUEST_BUDGET`, меньше
`proxy_read_timeout` nginx). Без него лестница не работает в главном сценарии:
остановленный контейнер не отказывает, а молчит, исключения не возникает,
`except` не выполняется, ожидания источников складываются — и пользователь
получает 504 вместо 200 с популярным. Поймано на стенде.

**У кэша есть предохранитель** (`RECS_CACHE_FUSE_SECONDS`): первая же неудача
гасит обращения к Redis на несколько секунд. Иначе два таймаута молчащего
контейнера на каждый запрос съедали бюджет раньше, чем очередь доходила до
PostgreSQL, — отказ ускорителя отменял работу источника истины.

## Схема витрины принадлежит этому сервису

`alembic.ini`, `migrations/`, модели — здесь, хотя **пишет** в витрину батч.
Причина в compose: контейнер миграций переиспользует образ сервиса, а выдача
живёт в ядре и поднимается всегда, тогда как батч сидит в профиле `warehouse`.
Батч пишет сырым SQL, второй копии моделей в репозитории нет.

Версия батча входит в первичный ключ каждой таблицы списков. Отсюда сразу два
системных требования: повторный прогон физически не может удвоить строки
(F0.1), а выдача видит целостный батч, а не половину нового поверх половины
старого (F0.2).

## Два Redis, и это не избыточность

`redis-recs` — горячий слой витрины (`volatile-lru`, TTL на ключах версии).
Ядровый `redis` — денилист отозванных токенов, который ведёт Auth и читать
который надо там же, где он пишется. Один клиент на оба назначения искал бы
денилист не в той базе — ровно на этом однажды обжёгся коллектор.

Политика при недоступном денилисте — **`deny`** (раздел 5.5 ТЗ): отозванный
токен не должен продолжать читать личную выдачу. Это строже коллектора
(`allow`) и совпадает с `ugc-api`.

## Почему отдельный сервис, а не ручка в Movies API

ADR-006. У рекомендаций другой профиль отказа (им можно деградировать, каталогу
нельзя), другое хранилище (витрина перезаписывается целиком) и другой темп
релизов. Ручка внутри Movies API сделала бы каталог зависимым от готовности
модели — страница фильма падала бы из-за блока рекомендаций.

## Эксплуатация

```bash
# Миграции витрины
npx nx run recommendations-api:migrate

# Тесты
npx nx run recommendations-api:test              # юнит
npx nx run recommendations-api:test-functional   # против живых recs-db и redis-recs

# SLO на проектных 100 RPS (p95 < 200 мс, p99 < 300 мс, 5xx нет).
# Снятые числа — docs/recommendations.md#замеры-slo: p95 43,9 мс, p99 47,8 мс.
# FILM_IDS обязателен: без него замер идёт по одному фильму, то есть по кэшу.
FILMS=$(docker compose --env-file .env -f infra/compose/docker-compose.yml \
    --project-directory infra/compose exec -T recs-db psql -U postgres -d recs_database \
    -t -A -c "SELECT string_agg(film_id::text, ',') FROM (SELECT DISTINCT film_id FROM similar_item LIMIT 200) s")
docker run --rm --network compose_movies_net -v "$PWD/loadtests:/scripts" \
    -e BASE_URL=http://nginx -e FILM_IDS="$FILMS" grafana/k6:0.55.0 run /scripts/recommendations.js

# Лимитер при этом остаётся включённым — что он жив, проверяется отдельно
docker run --rm --network compose_movies_net -v "$PWD/loadtests:/scripts" \
    -e BASE_URL=http://nginx grafana/k6:0.55.0 run /scripts/recs-limiter.js
```

100 RPS снимаются с восьми синтетических адресов (`X-Forwarded-For`), иначе
зона `recs_read` в 50 r/s **на адрес** делает проектную цифру недостижимой —
разбор в [`loadtests/README.md`](../../loadtests/README.md).

Метрики: `recs_requests_total{kind,source}` (доля деградации),
`recs_cache_*`, `recs_shelf_unavailable_total`, `recs_shelf_age_seconds`,
`recs_response_duration_seconds`. Алерты — `infra/monitoring/prometheus/alerts.yml`.

## Не сделано (осознанно)

- **Каталога в витрине нет и не будет.** В ней только идентификаторы и вес;
  названия отдаёт Movies API (F2.5). Копия карточек здесь была бы вторым
  экземпляром данных со своим собственным лагом — и это при том, что витрина
  перезаписывается целиком каждым прогоном батча.
- **Обогащение на горячем пути.** `?enrich=true` существует, чтобы стык с
  каталогом был проверяем, а не чтобы им пользовались под нагрузкой:
  bulk-ручки по списку идентификаторов у Movies API нет, и N позиций — это N
  запросов. Правильный ход — добавить такую ручку в каталог, и это работа в
  чужом сервисе.
- **A/B двух моделей одновременно.** Версия одна **на витрину**, а не на
  пользователя: она входит в первичный ключ таблиц списков и переставляется
  одним указателем. Сравнение двух моделей на живом трафике потребовало бы
  версионирования выдачи на уровне пользователя и второго набора таблиц —
  то есть смены контракта витрины, а не правки выдачи.
- **Объяснимость** («потому что вы смотрели X»). Витрина не несёт вклада
  признаков — только `film_id` и вес. Хранить его значит снова менять контракт
  витрины; цена возврата оценена в разделе 6 ТЗ.
- **Персонализация внутри сессии.** Учесть то, что человек посмотрел десять
  минут назад, нечем: ADR-001 разрезал систему на батч, который думает, и
  выдачу, которая только читает. Онлайн-слоя в этой архитектуре нет, и
  добавлять его ради одного сценария — отдельное решение, а не доработка.
- **Фильтрация по возрастному рейтингу и региональной доступности.** Открытый
  вопрос 4 ТЗ ([`docs/diploma-tz.md`](../../docs/diploma-tz.md), раздел 10), и
  там он прямо назван осознанным пропуском, а не недосмотром: правила
  доступности задаёт заказчик, а угаданные правила хуже отсутствующих — они
  выглядят работающими.
- **Своего ограничителя частоты.** Как и у `ugc-api`: третий форк лимитера
  упёрся бы в порог jscpd. Чтения закрыты зоной `recs_read` в nginx.
