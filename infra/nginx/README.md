# Nginx

Обратный прокси и балансировщик — единственная публичная точка входа платформы
(порт `80`). Распределяет трафик между сервисом выдачи контента (`api`),
сервисом авторизации (`auth`), административной панелью (`django-admin`) и
сервисом сбора пользовательских действий (`analytics-collector`), отдаёт статику
и обеспечивает сквозную корреляцию запросов через `X-Request-Id`.

## Функции

- Балансировка нагрузки и проксирование к upstream-сервисам (keepalive-соединения).
- Отдача статических файлов (`/static/` из `/data/static/`).
- Формирование и защита заголовка `X-Request-Id` для распределённой трассировки.
- Восстановление реального IP клиента из `X-Forwarded-For`.
- Ограничение частоты запросов и числа соединений (первый рубеж, до приложения).
- Ответ на CORS-preflight ingest-ручки без обращения к приложению.
- Разжатие сжатых клиентом тел запросов (`gunzip`).
- Ответ на отказ апстрима: JSON для `/api/*`, html-страница для маршрутов,
  которые открывает человек.

## X-Request-Id (корреляция и трассировка)

`nginx.conf` является **источником истины** для идентификатора запроса:

```nginx
proxy_set_header X-Request-Id $request_id;
```

Nginx генерирует `$request_id` и **перезаписывает** любой присланный клиентом
`X-Request-Id` (защита от подмены). Значение попадает и в access-лог — полем
`request_id` формата `json_access` (см. ниже), под тем же именем, что и в логах
приложений: один запрос в Kibana находит и строку nginx, и строки сервисов.
Приложения (auth / api / django) требуют
этот заголовок, проставляют его в OpenTelemetry-span, возвращают в ответе и
пробрасывают в исходящих межсервисных вызовах — так один запрос прослеживается
сквозь все сервисы в Jaeger. Коллектор — исключение: он генерирует идентификатор
сам, потому что `navigator.sendBeacon` не умеет ставить произвольные заголовки.

## Access-лог в JSON (`log_format json_access`)

Access-лог пишется в `/dev/stdout` одной строкой JSON. Его читает Filebeat и
разбирает Logstash (`infra/elk/`), поэтому формат согласован с логами
Python-сервисов: `timestamp`, `level`, `logger`, `message`, `service`,
`request_id` — плюс поля самого nginx.

| Группа | Поля |
|---|---|
| Общие с приложениями | `timestamp` (`$time_iso8601`), `level` (всегда `INFO`), `logger` (`nginx.access`), `service` (`nginx`), `message` (`$request`), `request_id` |
| Клиент | `remote_addr`, `remote_user`, `http_referer`, `http_user_agent`, `http_x_forwarded_for`, `scheme`, `protocol` |
| Запрос | `method`, `uri`, `args`, `request_length` |
| Ответ | `status`, `body_bytes_sent`, `request_time` |
| Апстрим | `upstream_addr`, `upstream_status`, `upstream_response_time`, `upstream_connect_time` |

Две вещи в этом формате сделаны намеренно и ломаются, если их «поправить»:

* **`escape=json` обязателен.** Без него кавычка или обратный слэш в
  `User-Agent`, `Referer` или URL рвёт JSON, и запись уезжает в
  `_jsonparsefailure`. Именно этими полями управляет клиент — то есть сломать
  лог можно намеренно.
* **Числа закавычены.** `$status` при обрыве соединения равен `000`, а `000` —
  невалидный литерал JSON (ведущие нули); `$upstream_response_time` бывает
  пустым и списком вида `0.001, 0.002`. Типы приводит Logstash уже после
  разбора (`infra/elk/logstash/pipeline/logs.conf`), и там же живёт список
  полей, которые становятся числами.

`error_log` не настраивается: официальный образ симлинкует его в `/dev/stderr`,
и строки попадают в тот же сборщик — Logstash помечает их уровнем `WARNING`, раз
у них нет нашего формата.

## Маршрутизация (`configs/site.conf`)

| Путь | Upstream | Примечание |
|------|----------|------------|
| `/static/` | `/data/static/` | статика |
| `/admin` | `django_upstream` | админ-панель Django |
| `^~ /api/v1/auth/{login,register,refresh}` | `auth_upstream` | жёсткий лимит `auth_login` (1 r/s, burst 5–10) |
| `^~ /api/v1/{auth,roles,users}` | `auth_upstream` | сервис авторизации (10s read / 5s connect) |
| `^~ /api/v1/events` | `analytics_upstream` | ingest, лимит `ugc_ingest` (50 r/s, burst 100), preflight на Nginx |
| `^~ /api/analytics` | `analytics_upstream` | документация коллектора |
| `^~ /api/v1/{likes,bookmarks,reviews}` | `ugc_upstream` | запись UGC, лимит `ugc_write` (20 r/s, burst 40) |
| `^~ /api/v1/ratings` | `ugc_upstream` | чтение рейтинга фильма, без лимита записи |
| `^~ /api/ugc` | `ugc_upstream` | документация сервиса UGC |
| `^~ /s/` | `shortener_upstream` | переход по короткой ссылке (слэш обязателен, см. ниже) |
| `^~ /api/shortener` | `shortener_upstream` | документация сокращателя (`POST /api/v1/links` маршрута не имеет намеренно) |
| `^~ /api/v1/recommendations` | `recommendations_upstream` | выдача рекомендаций, лимит `recs_read` (50 r/s, burst 100), таймауты 3s/2s |
| `^~ /api/recommendations` | `recommendations_upstream` | документация выдачи |
| `/api` | `api_upstream` | Movies API (перехватчик остального `/api`) |
| `^~ /health`, `= /metrics` | — | `404`: пробы и метрики снимаются внутри сети |
| `/` | `django_upstream` | всё остальное |

### Почему `^~`, а не порядок блоков

`location /api` — префиксный перехватчик **всего** `/api`. Раньше маршруты Auth
и коллектора работали только потому, что были объявлены **выше** него:
регулярные выражения проверяются в порядке объявления и выигрывают у
префиксного совпадения. Достаточно было переставить блоки местами — и события
поехали бы в Movies API с ответом 404, причём конфиг остался бы валидным, а
сервисы живыми: диагностировать такое тяжело.

Модификатор `^~` снимает эту зависимость: он имеет приоритет над регулярными
выражениями и над более короткими префиксами **независимо от места в файле**.
Порядок блоков теперь нужен только человеку.

Обратная сторона того же приоритета — `^~ /s/` пишется **со слэшем**: префикс
`/s` перехватил бы `/static/`, потому что `^~` не смотрит, где он объявлен.

## Ответ на отказ апстрима

Страницы лежат в `infra/nginx/html/` и монтируются в `/data/errors`
(`docker-compose.yml`, сервис `nginx`).

| Маршруты | Ответ | Почему |
|---|---|---|
| всё по умолчанию, то есть `/api/*` | `50x.json` | клиент сервиса ждёт код и тело, а не html |
| `/`, `/admin`, `/s/` | `50x.html` | сюда приходит человек |

Три вещи здесь сделаны намеренно и ломаются, если их «поправить».

**Обработчик — статический файл, а не `return`.** Файл сохраняет исходный код
ответа (клиент получает 502 или 504 с телом из файла), тогда как
`return 503 '...'` подменил бы код своим. Ровно на этом месте была прежняя
поломка: `location = /50x.html { root html; }` указывал на каталог,
которого в образе `nginx` нет, промах по файлу превращался в **404**, и любой
504 от медленного апстрима приезжал клиенту как «ничего нет» — то есть как
приглашение НЕ повторять запрос. В access-логе при этом честно стояло
`"status":"404","uri":"/50x.html","upstream_status":"504"`, и диагностировалось
это только по логу.

**`proxy_intercept_errors` выключен, и включать его нельзя.** Из этого следует,
что `error_page` срабатывает только на ошибки самого nginx — 502 (апстрима нет)
и 504 (`proxy_read_timeout`). Собственные 5xx приложений проходят насквозь, и
это обязательное свойство: лестница деградации рекомендаций и страницы
сокращателя ссылок (`templates/{404,503}.html`) отвечают клиенту сами, и
подменять их заглушкой прокси значило бы стереть разницу между «сервис думает,
что делает» и «сервиса нет».

**`error_page 404` не объявляется вовсе.** 404 приложений сюда не доходят (см.
предыдущий абзац), а единственные 404 самого nginx — промахи статики и заглушки
`^~ /health` / `= /metrics`, где страница не нужна. Прежняя строка
`error_page 404 /404.html;` указывала на несуществующий файл и не срабатывала
никогда.

## Ограничение частоты и числа соединений

| Зона | Область | Лимит | Зачем |
|------|---------|-------|-------|
| `ugc_write` | `/api/v1/{likes,bookmarks,reviews}` | 20 r/s, burst 40 | Единственный лимит без прикладного дубля: ugc-api намеренно не содержит своего лимитера. Порог ниже, чем у ingest: каждый запрос берёт блокировку и пишет в PostgreSQL |
| `ugc_ingest` | `/api/v1/events` | 50 r/s, burst 100 | Грубый флуд отсекается до Python; точный учёт (включая вес пачки событий) ведёт сам сервис |
| `auth_login` | `login`, `register`, `refresh` | 1 r/s, burst 5–10 | Брутфорс пароля не должен доходить до Python и Redis: проверка идёт через argon2 — намеренно дорогую функцию |
| `perip` (`limit_conn`) | весь сервер | 100 соединений с адреса | `limit_req` ограничивает частоту, но не число одновременных соединений — медленные соединения (slowloris) им не отсекаются |

Плюс `client_body_timeout` / `client_header_timeout` / `send_timeout` по 10 с —
без них медленное соединение удерживает воркер сколь угодно долго.

Прикладные лимиты (Redis fixed-window в `auth` и в коллекторе) остаются вторым
рубежом: они видят пользователя, а не только адрес.

## Реальный IP клиента

```nginx
set_real_ip_from 172.16.0.0/12;   # bridge-сети docker compose
set_real_ip_from 192.168.0.0/16;
set_real_ip_from 10.0.0.0/8;
set_real_ip_from 127.0.0.0/8;
real_ip_header   X-Forwarded-For;
real_ip_recursive on;
```

Раньше доверенной была одна подсеть `192.168.1.0/24`, в которую Docker-адреса
не попадают. Последствие конкретное и неочевидное: `$remote_addr` остаётся
адресом прокси, **все клиенты выглядят одним адресом**, и `limit_req` считает
их одним клиентом — лимит либо срабатывает ложно сразу на всех, либо не
срабатывает вовсе.

За облачным балансировщиком сюда нужно добавить **его** диапазоны и убрать
лишние: чем шире список доверенных сетей, тем проще подделать `X-Forwarded-For`.

## CORS

Preflight (`OPTIONS`) на `/api/v1/events` отвечается прямо в Nginx с
`Access-Control-Max-Age: 86400`, иначе каждый cross-origin POST трекера стоил бы
двух запросов, второй из которых тратит воркер Python на полностью статичный
ответ.

Источник берётся из `map $http_origin $cors_origin` в `nginx.conf`, а не
подставляется из запроса: возврат присланного `Origin` в
`Access-Control-Allow-Origin` равносилен `*`.

> Список источников в `map` **обязан совпадать** с `UGC_CORS_ALLOW_ORIGINS` в
> `.env`. Иначе запрос, прошедший preflight на Nginx, будет отбит самим
> приложением — два источника правды.

## Запуск локально

Обычно запускается в составе Docker Compose. Для отдельного запуска:

1. Установите Nginx.
2. Скопируйте конфигурацию:
   - `nginx.conf` → `/etc/nginx/nginx.conf`
   - `configs/site.conf` → `/etc/nginx/conf.d/site.conf`
3. Убедитесь, что сервисы `api`, `auth`, `django-admin`, `ugc-api` и `analytics-collector`
   доступны по именам хостов из `upstream`-блоков.
4. Перезапустите Nginx.

Проверка конфигурации без запуска стека:

```bash
docker run --rm \
    -v "$PWD/nginx/nginx.conf:/etc/nginx/nginx.conf:ro" \
    -v "$PWD/nginx/configs:/etc/nginx/conf.d:ro" \
    nginx:1.25.3 nginx -t
```

(Имена апстримов при этом не резолвятся — проверять синтаксис удобно на копии
конфига с подменёнными адресами.)

## Переменные окружения

Конфигурация статична и не использует переменные окружения напрямую.

## Дальнейшее развитие

**TLS и HTTP/2.** Сервис слушает только `:80`. Для сбора аналитики это значимо:
события содержат URL посещённых страниц и поисковые запросы, и в открытом виде
они видны любому промежуточному узлу. Кроме того, `navigator.sendBeacon` с
HTTPS-страницы на HTTP-эндпоинт блокируется как mixed content — то есть на
реальном сайте сбор просто не заработает. Нужны терминация TLS, редирект с 80 на
443 и HTTP/2 (мультиплексирование особенно полезно трекеру, шлющему много мелких
запросов). Не сделано здесь только потому, что требует сертификатов, которых у
локального стенда нет.

**Websocket-шлюза здесь нет, и это решение.** `apps/notifications-ws/`
публикуется прямым хост-портом (8091), потому что маршрут к нему потребовал бы
трёх правок сразу, а первая из них ломает стенд: Nginx резолвит апстримы при
старте и падает без профильного контейнера (см. выше про коллектор — там та же
причина решила судьбу профиля). Плюс глобальный `proxy_set_header Connection ""`
из блока keepalive прямо ломает handshake, а `proxy_read_timeout` в 5–10 секунд
рвал бы долгоживущее соединение. Понадобились бы `map $http_upgrade
$connection_upgrade`, отдельная location со своими заголовками и своими
таймаутами и `resolver` с переменным `proxy_pass` — то есть ровно тот размен
fail-fast на 502, который отвергнут выше. Панель нотификаций публикуется напрямую
по той же причине.

**Горизонтальное масштабирование апстримов.** Имя сервиса в `server` резолвится
один раз при старте Nginx, поэтому `docker compose up --scale
analytics-collector=3` сам по себе ничего не даёт. Параметр `server ... resolve`
есть только в NGINX Plus; в open source остаются два варианта — перечислять
реплики явными строками `server` либо использовать `proxy_pass http://$переменная`
с резолвером, теряя keepalive к апстриму. Выбрана статическая форма с keepalive:
для ingest-ручки новое TCP-соединение на событие дороже, чем даёт балансировка.
Подробности — в комментарии к `upstream` в `nginx.conf`.

**Сам Nginx — единственная точка отказа.** В compose он один. Для продакшена
нужен либо внешний балансировщик перед несколькими экземплярами, либо
keepalived/VRRP.
